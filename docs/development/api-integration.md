# 接口联调

实现公告示例后，按本页顺序检查接口、页面和授权是否衔接正确。

## 1. 先看实际请求链路

```text
list.vue / form.vue
  → src/api/notice.ts
  → requestClient（/api、Bearer、响应拆包）
  → Vite 代理 / 前端运行入口
  → NoticeController → INoticeService → Mapper → MySQL
```

基础服务的启动和代理设置见[快速开始](/getting-started/)。新增后端模块、Java 代码和资源后需重新构建并启动实际应用；前端使用开发服务时由 Vite 加载页面。

## 2. 用现有接口文档查看新接口

开发环境默认在 `http://127.0.0.1:8080/doc.html` 提供 Knife4j，OpenAPI 为 `http://127.0.0.1:8080/v3/api-docs`。端口以实际后端配置为准。

NoticeController 使用 @RestController、@RequestMapping 和 @Tag 后，正常进入应用运行类路径即可被扫描，不另建一份手工 Swagger JSON。看不到接口时先核对启动模块依赖和包扫描范围。

受保护接口需要本人登录得到的 access token。在 BearerAuth 输入框填写 access token，由文档工具构造 Bearer 请求头；不能把 AUTH_JWT_SECRET 当作登录令牌。调试图形验证码、首次改密、刷新和退出时仍遵守现有认证流程，不能为了调试关闭权限、CSRF 或 Origin 校验。

接口文档默认只在 dev/test 开放；正式环境不通过临时放行文档入口来完成测试。

## 3. 对照分页与写入结果

新增请求体：

```json
{
  "title": "欢迎使用公告管理",
  "content": "这是一条教学示例公告。",
  "status": 1
}
```

预期创建响应形状：

```json
{
  "code": 0,
  "data": { "id": "1" },
  "error": null,
  "message": "ok"
}
```

这里的 1 是示意 ID，后续请求使用本次创建实际返回的值。分页接口 `GET /api/notice/list?page=1&pageSize=20` 的 data 形状：

```json
{
  "items": [
    {
      "id": "1",
      "title": "欢迎使用公告管理",
      "content": "这是一条教学示例公告。",
      "status": 1,
      "createTime": "2026-10-28 10:00:00",
      "updateTime": "2026-10-28 10:00:00"
    }
  ],
  "total": 1
}
```

页面查询函数已经获得这个 data，不要再返回 `{ data: ... }` 给 Grid。更新、删除成功时 data 为 null，前端通过刷新列表展示结果，不等待一个并未约定的 updated 字段。

## 4. 在浏览器定位问题

打开开发者工具的 Network，检查实际请求 URL、方法、状态、请求体和响应：

| 现象 | 优先检查 |
| --- | --- |
| 请求变成 /api/api/notice | API 封装重复添加了 /api |
| 返回 HTML 或 Vite 页面 | 请求地址、开发代理目标和实际后端端口 |
| 404 或看不到公告接口 | 启动 Jar 是否包含新 biz 模块，Controller 映射是否一致 |
| HTTP 401 | 当前 access token、会话状态和是否需要重新登录 |
| HTTP 403 | 账号实际权限；Cookie 相关认证请求还需检查来源和 CSRF |
| 菜单保存提示组件未登记 | menu-components.txt、组件键、是否已加载新资源 |
| 页面存在但不显示菜单 | 节点状态、父级、角色授权和当前用户可见路由 |
| 列表无数据但接口成功 | data.items / data.total 形状、筛选条件、实际连接库 |
| 编辑后正文被清空 | 是否读取详情、加载失败是否禁止提交、DTO 是否只包含完整表单 |
| Java ID 变成不准确的数字 | HTTP VO、前端类型和是否误用了 Number(id) |

不要把“请求返回 HTTP 200”单独当作成功结论，普通业务响应还需要符合 code=0 及约定的 data。应用既有刷新接口有单独契约，本例公告接口不套用其返回方式。

## 5. 完成后的检查清单

下面由二次开发者在自己的开发环境执行，不是文档站的自动验收结果。

### 基础操作

- [ ] 新增标题、正文和状态，创建后使用实际 ID 查询详情。
- [ ] 查询支持页码和页大小，返回稳定排序的 items/total。
- [ ] 修改公告，列表与重新打开详情均显示新值。
- [ ] 删除后列表刷新，使用原 ID 查询返回 NOT_FOUND。
- [ ] 写操作留下对应操作码的审计，不将公告正文写入日志摘要。

### 参数与权限

- [ ] 空标题、超长标题/内容、非法状态被拒绝。
- [ ] page=0、pageSize=101、非十进制或超出 Long 范围的 ID 被拒绝。
- [ ] 没有登录不能读取公告接口。
- [ ] 仅有查询权限时能看列表，不能创建、编辑或删除；直接调用 API 也应被拒绝。
- [ ] 普通角色授权后菜单与按钮正确；授权变化按应用提示重新登录。
- [ ] 中英文切换后表头、表单和按钮文案正确，纯文本正文没有被当作 HTML 执行。

## 6. 代码检查与后续维护

实现者应在 frontend 按项目命令进行类型和格式检查，在 backend 按项目流程编译与验证。检查范围应覆盖本次新增模块与页面。

同时维护：新模块 POM、迁移版本、接口描述、页面组件白名单、菜单授权和语言词条。已有库的结构升级使用新迁移，不能为“重做教程”删除历史库或改旧脚本。

本章提供教学参考实现，实际接入时仍需按你的业务需求完成开发环境的构建和联调，不能只凭页面出现就判断功能完成。
