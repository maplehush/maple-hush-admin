# 数据库规范

MySQL 是业务数据的持久化来源，Redis 用于现有验证码、限流和缓存等能力。新增表和升级使用 Flyway，源码迁移文件比旧表结构截图更能反映当前结构。

## 命名与类型

| 对象 | 约定与示例 | 原因 |
| --- | --- | --- |
| 表名 | 小写下划线，现有 `sys_user`、`sys_role`、`auth_refresh_session` | 表名体现业务归属 |
| 字段 | 小写下划线，如 `role_code`、`create_time` | 与 Java 属性显式映射 |
| 主键 | 按业务模型使用有符号 `BIGINT`；普通实体通常自增 | 对齐 Java Long；关联表按关系建主键 |
| 状态 | 明确数值含义与允许范围，如 `0/1` | 避免前后端各自解释 |
| 时间 | 通常 `DATETIME`，按项目统一时区，秒精度 | 与接口时间约定一致 |
| 文本 | 按用途确定 VARCHAR 长度或 TEXT | 业务限制与存储能力分别说明 |
| 索引 | 现有 `uk_...`、`idx_...` | 从名称辨认唯一性和查询用途 |

当前系统表使用 InnoDB、`utf8mb4`；V1 系统表排序规则为 `utf8mb4_0900_ai_ci`。新增表应明确选择并核对排序规则，尤其检查大小写比较及唯一性语义，避免关联字段因类型或排序规则不同而难以连接。

前后端字段名不同需要显式转换，例如 `role_name` 对应接口 `name`。不能凭数据库列名推导公开 API 字段。数据库 ID 到接口字符串的转换见[接口规范](./api.md)。

## 公共字段与关联表

普通业务实体的 `create_time`、`update_time` 对应公共实体的创建、更新时间；写入方式应与现有填充处理一致。Wrapper 或自定义 SQL 更新需显式维护修改时间。

不要要求所有表都有自增 ID、状态或修改时间。例如 `sys_user_role` 使用 `(user_id, role_id)` 复合主键，记录授权关系和创建时间即可。

布尔语义字段与 Java 属性分别命名，避免依赖隐式推断：`is_builtin` 映射 `builtIn`，`is_default` 映射 `defaultItem`。

## 约束与并发

数据库约束承担最后一道数据一致性保障。当前系统表已经使用主键、唯一键、外键和 CHECK，项目没有“禁止所有外键”的约定。

例如 V1 的用户角色关系：

```sql
PRIMARY KEY (user_id, role_id),
KEY idx_sys_user_role_role_user (role_id, user_id),
CONSTRAINT fk_sys_user_role_user
    FOREIGN KEY (user_id) REFERENCES sys_user (id) ON DELETE RESTRICT,
CONSTRAINT fk_sys_user_role_role
    FOREIGN KEY (role_id) REFERENCES sys_role (id) ON DELETE RESTRICT
```

复合主键防止重复授权，反向索引支持按角色查用户，外键防止孤立关系。Service 仍需要校验目标范围、删除条件和并发状态；不能仅依赖约束抛出的数据库原始错误。

唯一性预检查与最终写入之间可能有其他事务插入，不能只靠“先查再插”。使用数据库唯一键并通过现有异常处理给出安全的冲突响应。

## 索引与查询

根据实际过滤、连接和排序条件设计索引，说明对应查询。组合索引的列顺序影响可用性，不为每个字段机械地加单列索引。

新增或修改查询时检查：

- 返回列、分页大小及排序是否受控。
- 是否存在全表加载后在 Java 内存分页。
- 组合索引能否支持主要筛选和排序，是否重复已有索引。
- 批量更新、删除是否有限定范围，是否需要分批处理。
- 有序列表在排序值相同时是否仍有稳定顺序。

数据量相关的性能问题应在实际数据规模下分析执行计划；不能用少量样例数据证明查询长期没有性能问题。

## Flyway 迁移

统一目录：`backend/admin-system-start/src/main/resources/db/migration/`。当前源码包含 V1～V10，目标环境实际已执行到哪个版本，应查看自己的 Flyway 历史记录。

新增脚本使用 `V<版本>__<说明>.sql`，例如 `V<N>__add_notice_index.sql` 中的 `<N>` 需替换为实际未占用数字。双下划线不可省略。多人开发先协调版本，再提交到同一迁移序列。

1. 阅读现有迁移，确认字段、约束和数据状态。
2. 选择全工程唯一的新版本，编写结构或数据升级。
3. 检查存量数据能否满足新约束，必要时先设计回填和异常数据处理。
4. 在自己的开发或测试数据库验证升级，并记录结果。
5. 与实体、Mapper、接口和前端改动一起审查。

**已经执行并共享的历史迁移不能直接修改。** 修正通过新迁移追加，避免校验和不一致或不同环境结构分叉。不要手工执行脚本后，再让 Flyway 重复执行同一变更，也不要通过清空历史表解决版本冲突。

新增功能的建表示例见[数据库与接口](/development/database-api)。迁移脚本不创建数据库、不写死其他环境的数据 ID 或真实密码。

## 数据变更审查

提交前说明变更原因、影响的表、存量数据处理、预期执行量及兼容影响。新增非空列、修改类型、删除字段、建立唯一索引等，都需要检查现有数据是否满足条件。

密码保存安全哈希，不保存明文。刷新会话等敏感数据沿用当前散列与撤销机制，不在迁移中新增演示 token 或真实凭据。备份、升级窗口与恢复方案属于实际发版准备，不能用“删库重建”替代升级设计。
