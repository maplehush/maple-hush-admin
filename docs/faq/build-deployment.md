# 构建与代码更新

本页先收录工具链、构建和配置加载问题。正式服务器部署故障排查随[部署运维](/deployment/)教程验证后补充。

## 为什么 frontend 与 docs 的 pnpm 版本不同？

**现象：** 在不同目录执行 pnpm 显示不同版本，或前端安装时提示工具版本不符。

**排查：** 先确认当前目录，再查看该工程的 `package.json`、`packageManager` 与 `engines`；在同一目录检查 `node --version` 和 `pnpm --version`。

**原因：** frontend 与 docs 是独立工程，分别锁定 pnpm 11.16.0 和 12.3.4。前端还依赖完整 workspace，不能只安装应用子目录。已确认的本地使用方式为直接运行 pnpm，避免 `corepack pnpm install` 的子脚本落到不同全局版本。

**处理：** 前端按[下载与安装](/getting-started/installation#安装前端依赖)，在 `frontend/` 使用固定版本和已有锁文件；文档使用 `docs/` 的独立配置。不要删除锁文件或修改 packageManager 来绕过不匹配。

**核对结果：** 两个工程各自使用声明的版本，安装没有意外修改锁文件。版本相同不保证安装一定成功，还需区分网络与依赖脚本错误。

## 下载依赖超时，是不是代码有问题？

**现象：** 安装或构建在下载 pnpm、npm 包、Maven 发行包或依赖时出现连接超时。

**排查：** 从错误中找具体 URL、失败阶段和执行环境。确认失败的是下载工具本身还是下载业务依赖；宿主机可以访问不代表另一个构建环境也可访问。

**原因：** 超时只说明该次访问未在时限内完成，不能直接证明代码或锁文件错误。Corepack 下载 pnpm 发生在 pnpm 安装依赖之前，仅调整 pnpm 的 registry 不一定覆盖前一步。

**处理：** 核对失败环境的网络、DNS、代理和实际下载源；按当前工程入口配置。当前前端 Dockerfile 已通过 `COREPACK_NPM_REGISTRY` 与 `npm_config_registry` 对接 `NPM_REGISTRY` 构建参数，不要把修改宿主机全局源当作已改变镜像内配置。正式服务器源配置步骤留待部署文档补充。

**核对结果：** 原来失败的下载阶段通过，构建继续进行；后续编译报错要另外处理。不要为超时删除锁文件、关闭 TLS 校验，或将不明镜像站配置成长期依赖源。

## 改了代码，为什么运行的还是旧内容？

**现象：** 已修改或拉取源码，重启后页面、接口或配置没有变化。

**排查：** 确认实际运行的是开发服务、Jar、静态 dist 还是容器镜像，并核对启动路径与当前提交。先确定进程使用的产物，避免反复修改没有被加载的源码。

**原因与处理：** 不同运行方式加载代码的时机不同：

| 运行方式 | 修改后的处理 |
| --- | --- |
| Vite 开发服务 | 一般 Vue/TS 改动热更新；启动环境或代理配置改变后重启开发服务 |
| `java -jar` | Java 或打包资源改变后，重新打包并启动新 Jar；运行参数改变后重新启动进程 |
| 已构建的前端 dist | 重新构建，并让实际静态服务提供新的产物 |
| 容器镜像 | 源码改变需构建新镜像并更新容器；restart 不会编译源码，`--no-build` 明确不构建 |

**核对结果：** 当前进程或静态入口使用最新产物，原变更已经可见。只拉代码、只重启旧 Jar 或旧镜像都不等于已经更新应用。具体构建命令见[下载与安装](/getting-started/installation)与[开发规范](/standards/)。
