## 1. 通用传输与错误

前端 `.env.development` 使用 `VITE_GLOB_API_URL=/api`；[目标应用请求器](../../frontend/apps/web-antdv-next/src/api/request.ts)对普通请求设置 `responseReturn: 'data'`，并用 `code=0` 判定成功。普通成功示例：

```json
{"code":0,"data":{"items":[],"total":0},"error":null,"message":"ok"}
```

本文件下表的“成功 `data`”列给出**每个接口的 JSON `data` 示例**，除 refresh 特例外都放入上述四字段响应壳；`data:null` 表示成功但无正文。失败列引用下表，代表对应 HTTP 状态和完整 JSON 示例。错误码从本项目设计起固定，非声称上游 mock 已实现；T02 建公共错误码，T04 起按任务实现并验证。

| 代号 | HTTP / 业务码 | 完整失败 JSON 示例 | 场景 |
| --- | --- | --- | --- |
| E400 | 400 / 40010 | `{"code":40010,"data":null,"error":"INVALID_ARGUMENT","message":"请求参数无效"}` | 字段格式、数量或缺失 |
| ECAP | 400 / 40011 | `{"code":40011,"data":null,"error":"CAPTCHA_INVALID","message":"验证码无效，请重新获取"}` | 验证码缺失、错误、过期或已使用 |
| EAUTH | 401 / 40100 | `{"code":40100,"data":null,"error":"UNAUTHENTICATED","message":"请重新登录"}` | access/refresh 缺失、失效或账号凭据错误；登录错误不泄露账号是否存在 |
| EFORB | 403 / 40300 | `{"code":40300,"data":null,"error":"FORBIDDEN","message":"没有操作权限"}` | 身份有效但权限不足 |
| ECSRF | 403 / 40301 | `{"code":40301,"data":null,"error":"CSRF_INVALID","message":"请求校验失败，请重试"}` | CSRF 或来源校验失败；前端不得对此触发 refresh |
| ECON | 409 / 40900 | `{"code":40900,"data":null,"error":"CONFLICT","message":"数据已变更或已存在"}` | 名称重复、关联阻止删除或并发冲突 |
| ERATE | 429 / 42900 | `{"code":42900,"data":null,"error":"RATE_LIMITED","message":"操作过于频繁，请稍后再试"}` | 验证码/登录限流 |
| EDEP | 503 / 50300 | `{"code":50300,"data":null,"error":"DEPENDENCY_UNAVAILABLE","message":"服务暂不可用，请稍后重试"}` | Redis 等必需依赖故障 |

受保护请求携带 `Authorization: Bearer <accessToken>`，无身份为 401、已认证但无权为 403。ID 在 JSON 与路径中均为十进制**字符串**，避免 JavaScript 精度损失。管理列表成功结构固定为 `{"items":[...],"total":1}`；Playground [Vxe 表格适配器](../../frontend/playground/src/adapter/vxe-table.ts)读取 `items/total`。所有时间输出为 `Asia/Shanghai` 本地时间的 `yyyy-MM-dd HH:mm:ss`；不会附 `Z`。查询筛选的 `startTime/endTime` 是日期 `YYYY-MM-DD`，后端按东八区整日区间解释，结束日包含全天。前端 [date-range-codec](../../frontend/playground/src/utils/date-range-codec.ts)当前正是这样编码；列表页由前端发送 `page/pageSize`，不发送 `pageNo`。默认 `page=1,pageSize=20`，上限 100。

目标应用 [Vite 开发代理](../../frontend/apps/web-antdv-next/vite.config.ts)目前将 `/api` 重写为空再代理到 `http://localhost:5320/api`，实际 mock 收到的仍是一个 `/api`。T14 切换真实后端时须同步调整代理 target/rewrite，保证对外和后端都只有一个 `/api`，不出现 `/api/api`。生产采用同源 TLS 入口。目标应用现有 `loginApi` 尚未显式 `withCredentials`，同源登录 Cookie 可由浏览器接收；T14 仍须在开发代理和正式入口实测 Cookie 行为。刷新/退出已有 `withCredentials: true`。

正常登录设置 `mh_refresh` Cookie；待改密分支不设置它，也不返回普通 access。refresh 令牌族从首次登录起最长 7 天，轮换不续期，access 默认 15 分钟。生产 refresh Cookie 为 `HttpOnly; Secure; SameSite=Lax; Path=/api/auth`、host-only；`dev` 为本机 HTTP 联调关闭 `Secure`。CSRF Cookie 同样限制 host-only、`Secure`、`SameSite=Lax`、`Path=/api/auth`，且 `HttpOnly`。前端从 `GET /api/auth/csrf` 的 `data.token` 取得提交值，刷新/退出同时送 Cookie 与 `X-XSRF-TOKEN`；登录/退出后重新获取 CSRF 凭据，服务端还校验请求来源。access 已过期仍可用有效 refresh Cookie 与 CSRF 退出；无有效 refresh 时退出幂等清 Cookie。退出、改密或管理员重置后，旧 access 下次请求失效。T05 已落地 Cookie 写接口的 CSRF 与来源校验；T14 合并同页并发 401 并协调多标签页刷新，不能重复提交旧 refresh。

T05 的 CSRF Cookie 名为 `mh_csrf`，JSON `data.token` 为 Spring Security XOR 处理后的提交值；客户端只从 JSON 读取，不能直接把 Cookie 值当请求头。refresh/logout 只接受 `X-XSRF-TOKEN`，不接受查询参数或表单参数替代。登录成功、首次改密成功和退出清除旧 CSRF Cookie；refresh 401 清除两类 Cookie，503 保留原会话以便重试。登录/refresh/logout 校验 `Origin`，缺少时校验 `Referer`；两者均缺少或来源不符返回 ECSRF。`dev` 默认允许 Vben 的 `http://localhost:5999`、`http://127.0.0.1:5999` 及后端本身来源，`test/prod` 必须配置精确的 `AUTH_ALLOWED_ORIGINS`。这里不信任 `Forwarded`/`X-Forwarded-*` 来推断来源；正式同源入口在部署时显式配置。Redis 清理失败不会阻止已经完成数据库撤销的退出。

[UserInfo 类型](../../frontend/packages/types/src/user.ts)继承的 [BasicUserInfo](../../frontend/packages/@core/base/typings/src/basic.d.ts)要求 `userId/realName/avatar/username`；它还保留演示用 `desc/token` 字段，T14 应调整目标应用类型或映射，不能为了满足演示类型再把 token 放进当前用户资料响应。上表加入本项目的 `introduction`。目标应用个人中心 [资料表单](../../frontend/apps/web-antdv-next/src/views/_core/profile/base-setting.vue)当前把 `roles` 作为可编辑的 mock 标签，T16 须改为只读。当前 [改密表单](../../frontend/apps/web-antdv-next/src/views/_core/profile/password-setting.vue)只显示成功提示，T16 对接本人改密 API。现有登录页自动填演示密码并使用 `SliderCaptcha`，T14 改为后端图片验证码。

T06 已落地上表三个 GET 查询接口，普通响应仍使用 `Result`，用户 ID 是字符串，`homePath` 当前为已存在的 `/dashboard/workspace`，不返回演示用 `token/desc` 或 `authVersion`。权限码按字典序去重；路由保留相对子路径，按钮与数据库管理字段不返回，缺省根目录组件为 `BasicLayout`，空子节点省略 `children`。可选用户资料字段允许 `null`，T14 前端须按实际响应处理头像和简介默认值。

唯一超管不得由用户管理接口停用、删除、重置或改角色；前端隐藏入口，后端直接请求同样拒绝。管理员重置别人时自己不退出。`username` 为登录账号，管理页 `name` 映射 `sys_user.real_name`，`remark` 不等于个人资料 `introduction`。

T10 已实现上述七个用户管理接口。详情/分页行的实际 VO 为 `id/username/name/deptId/roleIds/status/remark/createTime/updateTime`，用户、部门、角色 ID 均输出字符串，未分配部门为 null，角色列表稳定按 ID 升序（包括已关联停用角色）。分页按用户 ID 升序；`name` 仅筛选真实姓名，不把 username/remark/introduction 混为一谈。Mapper 的管理查询和 VO 不返回密码、哈希、refresh 凭据及授权版本。

- 创建账号和姓名分别非空、至多 64/100 字符；去除首尾空白后保存。账号创建后不可修改。`remark` 至多 500，`deptId` 是现存部门的正整数 ID，表单 null/空白/`"0"` 表示不分配；部门停用不自动停用用户。
- 创建时 status 缺省 1、roleIds 缺省空集合；非空 roleIds 另外要求 assign-role。角色分配是全量替换，`[]` 清空、null 拒绝，最多 100 个正整数 ID，重复 ID 去重；不存在角色或新分配停用角色返回 E400；原已关联停用角色可在角色全量替换时保留，不能新增给其他用户。内置角色/越权返回 EFORB。
- 普通操作者只能管理角色菜单范围不超出本人有效授权的目标用户；拟分配角色的原始菜单集合也必须在此范围，不能通过重置、删除或剥夺高权限普通账号绕过范围校验。超管角色不进入普通授予流程，超管账户身份按角色关联识别。
- 用户更新为资料全量表单：`name` 必填，`deptId` 为空/0 清除部门、`remark` 为空清除原备注，status 省略/null 保留。更新 DTO 不含 username、roleIds、密码、头像或本人 introduction；创建/更新/角色表单未知字段返回 E400，不能把敏感字段被忽略当作修改成功。
- 停用账号的启用会恢复既有角色能力，除 update 外还须 assign-role 并校验目标当前角色范围。既有停用角色可保留，不因此赋予停用角色权限。
- 资料修改只清快照并保留会话；状态发生变化、角色实际变化和密码重置均递增 authVersion、撤销目标 refresh 会话并在提交后清快照。同一角色集合重提为幂等，不额外踢出。重置仅影响目标用户（本人重置自己也失效）；唯一超管拒绝停用、删除、重置及任何角色变更，允许正常姓名/部门/备注编辑。
- 删除在同一事务中先使目标会话失效，清理 refresh 行和角色关联，再删用户；登录和操作审计快照保留。新建/重置只存 `12345678` 的 BCrypt 哈希，响应不含临时密码，待改密登录只返回专用短期凭据。个人中心本人旧密码/新密码改密仍由 T13 实现。
- 分页 page 从 1 开始、pageSize 为 1～100；姓名至多 100、deptId 筛选为正整数、状态 0/1、日期为有效 YYYY-MM-DD。开始/结束日均按东八区整日闭区间查询，反向/无效日期返回 E400。目标不存在返回 404、唯一账号/外键关联冲突返回 ECON。

### T11 字典接口实施细节

T11 已实现表中 11 个字典接口（含补充的字典项详情）；日志接口仍待 T12。现有 V2 已包含 `SystemDict` 页面节点和 `system:dict:list/create/update/delete`，本轮不新增重复节点或迁移。管理接口使用对应权限码；`GET /api/system/dict/type/{dictCode}/items` 仅要求已登录，不要求字典管理权限。

- 类型 VO 为 `id/dictCode/name/status/remark/createTime/updateTime`；字典项 VO 为 `id/dictTypeId/label/value/color/sort/defaultItem/status/remark/createTime/updateTime`。ID 为字符串，时间为东八区秒级；普通选项只有 `label/value/color/defaultItem`，不含管理备注。
- 类型 `dictCode` 创建必填，限定小写字母开头、字母/数字/下划线、至多 100 字符，创建后不可改；更新可省略或回传原值，变码返回 ECON。`name` 非空至多 100，映射 dict_name。
- 字典项 `dictTypeId` 必须是现存类型的正整数 ID；更新必须回传原类型，跨类型移动返回 ECON。`label/value` 非空至多 200，去除首尾空白，同类型 value 唯一、不同类型允许同值，数据库唯一约束兜底返回 ECON。
- `remark` 至多 500，空值清除。颜色只接受 null、空字符串或 `#RRGGBB`，HEX 大小写均接受并转小写保存；空值清除旧颜色，未知字段拒绝。颜色和 defaultItem 均不自动启停字典项。
- status 创建缺省 1、更新省略/null 保留；sort 创建缺省 0、更新省略/null 保留，接受有符号整数；defaultItem 创建缺省 false、更新省略/null 保留。设置 true 在所属类型行锁下清旧置新，发生重复值等错误时整体回滚；同类型包含停用项在内至多一个默认项。删除默认项后允许没有默认项，不自动选择其他项。
- 类型/项列表均返回 `items/total`，page 从 1 开始、pageSize 为 1～100。类型支持 dictCode/name 包含筛选、0/1 状态；字典项必须提供 dictTypeId，可按 label 包含及状态筛选。管理查询包含停用数据。
- 仅支持 `sortBy` 和 `sortOrder=asc|desc`：类型排序键为 `id/dictCode/name/createTime`，默认 id；项排序键为 `sort/id/label/value/createTime`，默认 sort。默认升序，非 ID 排序追加 ID 升序保证分页稳定；无效键或方向返回 E400，列名由后端 Lambda 映射。
- 普通编码查询只返回启用类型下的启用项，按 sort/id 升序。停用类型返回 `[]`；不存在类型/项返回 404。默认项若被停用，不会在普通结果中出现，也不会自动指定其他默认项。
- 类型包含任何项（包括停用项）时删除返回 ECON，须先显式删除关联项；字典项删除不删除类型。六个写操作使用已有字典 create/update/delete 操作码，审计目标类型区分 dict_type/dict_item，成功和失败均沿用独立审计事务。
- 字典变更不改变用户/角色权限，不递增 authVersion，不踢出当前用户；本轮不增加字典缓存，提交后的查询直接读取 MySQL。类型/项更新采用全量文本资料，前端切换状态或默认项时也须携带必填表单字段。
