# 后端接口文档与调试

## Apifox Helper 目录命名

Knife4j 从运行中的 OpenAPI 定义读取 `@Tag`，IDEA 插件直接解析源码，默认使用 Controller 类注释首行作为目录名。因此 Controller 类注释首行统一为与 `@Tag(name)` 相同的短名称，详细职责写入后续段落。

`backend/.apifox-helper.properties` 设置接口名读取 `@Operation(summary)`，并通过官方 `ignore=#ignore` 规则忽略测试辅助 Controller。配置不包含令牌或 Apifox 项目绑定信息。

重新上传时，建议在 `admin-system-biz/src/main/java` 下选择生产 Controller 范围，不选择整个含测试源码的工程。IDEA 需要读到本次项目内插件配置；如插件未重新读取配置，重新打开工程或刷新插件配置后再试。

已经同步到 Apifox 的旧目录和测试接口不会因源码调整自动消失。先核对接口方法、URL、用例和历史，再将业务接口整理到对应短名称目录，最后清理确认无用的空目录与测试接口；不直接删除仍有业务接口的长名称目录。官方规则见 [Apifox 可配置规则](https://docs.apifox.com/doc-5801721)及[插件同步说明](https://docs.apifox.com/apifox-idea-plugin)。本轮只修正本地源码与插件规则，未访问用户 Apifox 项目或上传接口。

## 访问入口

启动更新后的后端并启用 `dev` 或 `test` profile，直接访问后端同源地址：

- Knife4j Next：`http://localhost:8080/doc.html`
- OpenAPI JSON：`http://localhost:8080/v3/api-docs`

这里使用后端端口，不是前端 5999。代码或注解变更需在后端重启或热更新生效后刷新文档。

项目使用社区维护的 **Knife4j Next 5.7.9**，不是原项目 Knife4j 4.5.0；依赖为 `com.baizhukui:knife4j-openapi3-boot4-spring-boot-starter`。Starter 配套 springdoc 3.0.3 和 Swagger Jakarta 2.2.55，项目继续使用原有 Spring Boot 4.1.1。版本、增强能力和维护来源见 [Next 版本对照](https://knife4jnext.com/reference/version-ref)及 [Next 项目说明](https://knife4jnext.com/)。

## 开关和环境

- 公共 `application.yml` 默认关闭 springdoc 定义、Swagger UI 和 Knife4j；`application-dev.yml`、`application-test.yml` 开启。
- 安全链额外要求启用 `dev` 或 `test` 且未混合 `prod`，否则拒绝文档、定义和 WebJar 静态资源，即使误开启生成器开关也不放行。
- 不给业务接口新增匿名权限，不绕过菜单权限、验证码、来源检查或 CSRF；生产 Compose 不需要增加文档地址映射。
- 含首次改密凭据、访问令牌、Cookie 的调试结果不要提交仓库或分享截图；不要把真实密码写进注解示例。

## 登录和 Bearer 调试

1. 从“认证登录”调用 `GET /api/auth/captcha`，用返回的验证码图像完成登录输入。
2. 调用 `POST /api/auth/login`，填写账号、密码、captchaId、captchaCode。验证码一次性使用，失败重试需重新获取。
3. 普通登录从 `data.accessToken` 获取凭据，在“OpenAPI 鉴权”中填写 `BearerAuth`，仅填令牌本身；工具添加 `Bearer` 前缀。
4. 随后调试“当前用户与权限”中的用户信息、权限码等只读接口。管理写接口仍需当前账号拥有对应权限。
5. 首次登录返回 `passwordChangeRequired=true` 和 `passwordChangeToken` 时，将该专用凭据填入 `InitialPassword`，调用首次改密接口；完成后重新登录。普通 accessToken 不能代替首次改密凭据。

## Cookie、刷新和 CSRF

登录会设置 `mh_refresh` HttpOnly Cookie。浏览器同源调试应使用 UI 的 Cookie 会话携带策略；Cookie 由浏览器管理，不能通过 JavaScript 读取或手工拼接 Cookie 请求头。

刷新或退出前：

1. 在同一浏览器、同一主机名下调用 `GET /api/auth/csrf`。
2. 把返回的 `data.token` 填入 refresh/logout 接口的 `X-XSRF-TOKEN` Header 字段；不要复制 HttpOnly Cookie 值。
3. 调用 `POST /api/auth/refresh` 或 `POST /api/auth/logout`。来源必须通过校验；本地 dev 支持后端同源 Origin/Referer。不建议来回切换 `localhost` 和 `127.0.0.1`，两者 Cookie 不共享。
4. 登录、退出或 CSRF 校验失败后，重新获取 CSRF token 再操作。

**响应特例**：refresh 成功返回 JSON 字符串形式的 accessToken，未使用 `Result` 包装，这是已有前端传输约定；不要按 `data.accessToken` 解析。登录及其他常规接口使用 `code/data/error/message`，分页数据是 `items/total`。

Cookie 会话功能与 OpenAPI 鉴权是两种不同调试机制；在鉴权框填写 `RefreshCookie` 不会凭空创建有效的 HttpOnly 登录会话。测试工具需要保留服务端 Set-Cookie，并为认证写请求设置可信 Origin。

## 参数与响应约定

- Controller 使用 `@Tag` 分组和 `@Operation` 描述接口；路径及查询参数补充 `@Parameter`。
- DTO/VO 与公共响应使用 `@Schema`，密码字段标记为仅写；示例仅使用占位值。
- 日志查询原本接收 Map，已显式声明支持的查询字段；上传接口文档明确单个 multipart `file`，不增加实际上传字段。
- 公共错误结构及稳定错误码在文档首页的“通用错误响应”中集中说明，不再向每个接口重复添加通用错误响应表。401 为凭据问题，403 为权限或 CSRF 问题，429 为限流，503 为必要依赖不可用。具体错误取决于接口和请求条件，运行时错误处理保持不变。
- ID 使用十进制字符串；时间为 Asia/Shanghai，`yyyy-MM-dd HH:mm:ss`。
- 代码位置：公共注解依赖在 `admin-base-core`；Next Starter 和 OpenAPI 定制在 `admin-system-start`；文档访问策略接入业务安全链。

## 业务响应码

常规响应中 `code=0` 表示业务成功，非零表示业务失败。HTTP 状态与业务 `code` 是不同字段。下表以 `ResultCodes` 和 `ErrorCode` 的实际定义为准，在线文档首页也提供完整说明。

| code | error | HTTP 状态 | 含义 |
| --- | --- | --- | --- |
| 0 | 空 | 200 | 业务成功 |
| 40000 | BAD_REQUEST | 400 | 请求格式错误，如 JSON 无法解析或参数类型错误 |
| 40010 | INVALID_ARGUMENT | 400 | 参数不符合校验规则 |
| 40011 | CAPTCHA_INVALID | 400 | 验证码错误、过期或已使用 |
| 40100 | UNAUTHENTICATED | 401 | 未登录、凭据过期或无效、会话失效；登录时也用于账号或密码错误 |
| 40300 | FORBIDDEN | 403 | 没有操作权限 |
| 40301 | CSRF_INVALID | 403 | CSRF 凭据或请求来源校验失败 |
| 40400 | NOT_FOUND | 404 | 目标不存在或已删除 |
| 40900 | CONFLICT | 409 | 唯一约束、资源关联或并发状态冲突 |
| 42900 | RATE_LIMITED | 429 | 请求过于频繁 |
| 50000 | INTERNAL_ERROR | 500 | 服务器内部异常 |
| 50300 | DEPENDENCY_UNAVAILABLE | 503 | 必要依赖暂不可用 |

登录过期统一返回 HTTP `401`、`code=40100`、`error=UNAUTHENTICATED`，不单独区分令牌过期与其他凭据失效。受保护接口返回 401 时可尝试刷新令牌，刷新失败再重新登录；登录接口自身的 40100 不应触发刷新重试。`message` 是展示文案，业务判断使用 `code` 或 `error`。
