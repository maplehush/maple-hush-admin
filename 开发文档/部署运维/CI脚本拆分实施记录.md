## 设计与实施计划

目标：工作流只保留编排与 Docker Actions，按职责提取脚本，保持正式 Tag 触发、镜像复用与摘要锁、生产加锁、备份、健康检查和失败状态处理。

方案比较：单纯减少空行不能解决职责混合；拆成多个工作流增加跨流程衔接；本次选择单工作流配合三个 runner 脚本和一个服务器脚本。来源为本轮用户批准的设计，不引入自定义 Action 或新的发布平台。

- [x] 提取版本校验和镜像检查：环境变量、GITHUB_OUTPUT 名称不变，通过临时真实 Git 仓库验证校验规则。
- [x] 提取服务器 deploy.sh：保留现有远程部署体；部署 Job 检出同 Tag 的脚本内容，SSH 脚本传至 root 临时文件、核对 SHA-256，保存带版本/提交/运行号的文件，以关闭标准输入的方式执行。
- [x] 精简 ci.yml：保留四个 Job、依赖、并发组、Secrets 和 outputs，部署 Job 增加检出发布代码步骤；固定新 shell 脚本 LF 换行。
- [x] 验证及文档：检查 YAML、Actionlint、Shell 语法，测试版本校验、传输校验及错误传播；补充服务器无需迁目录/改配置的说明和未验证边界。

接口：runner 脚本从现有环境变量读取参数；服务器 deploy.sh 继续接收版本、源码 SHA、前后端镜像摘要、运行号、生产 Origin 六个位置参数。登录密码只经 SSH stdin 输入 Docker login；脚本上传单独使用 stdin；部署文件执行 stdin 为 /dev/null。

重点检查：最高版本重跑与旧版本拒绝、非 main 提交、摘要核对失败、上传/执行失败传播、正常及提前退出；本机无真实 Docker/SSH 目标，替代进程测试不等于真实 TCR 或服务器部署验收。
