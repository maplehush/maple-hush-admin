# 日常版本发布流程

适用于已有服务器环境，通过 `.github/workflows/ci.yml` 发布前后端镜像并更新生产容器。首次安装、数据库初始化、域名与证书配置不在本流程内。

2026-11-18：v0.1.4 的服务器截图确认前后端健康、成功记录和运行摘要一致；随后用户手动执行下述 Git 流程，反馈 v0.1.5 发布成功。v0.1.5 的服务器状态未由助手独立检查。这里记录日常操作方法，不代表所有故障和回退场景均已验收。

## 发布前确认

- 日常修改在 `develop` 完成，待提交文件均属于本次发布，不含真实 `.env`、密钥或生成产物。
- GitHub Actions 已配置 TCR 和 SSH Secrets；生产环境已运行 MySQL、Redis、Nginx，正式 HTTPS 入口正常。
- 当前一次正式 Tag 同步发布前后端；虽然保留两个版本变量，本流程仍将它们更新为同一版本。
- 选定新版本，高于远程已有正式 Tag 和服务器当前两个版本。Git 不自动递增版本号，由发布者填写，流水线负责校验。
- 涉及数据库迁移时，先审查兼容性。脚本备份不等于已经验证可回退。

以下 `v0.1.5` 是本次已发布版本的历史示例。下次发布必须统一替换成尚未使用的新版本，例如无更高版本时使用 `v0.1.6`；不要重新创建或覆盖 `v0.1.5`。

## 1. 提交并推送 develop

在本地产品仓库根目录执行；每条命令成功后再执行下一条，任何报错都先停下处理。PowerShell 粘贴多行命令不会自动在失败时停止，建议逐条执行。

```sh
git switch develop
git pull --ff-only origin develop

git status
git diff
```

如已有未提交修改导致拉取被拒绝，先妥善保存修改，再同步分支，不使用强制覆盖。确认变更内容后提交：

```sh
# 仅在确认全部改动均应提交后使用 git add .；否则逐个指定文件。
git add .
git diff --cached
git commit -m "fix: 描述本次修改内容"
git push origin develop
```

提交消息换成实际内容：修复用 `fix:`，新增功能用 `feat:`，文档用 `docs:`。

到 [GitHub Actions](https://github.com/maplehush/maple-hush-admin/actions) 确认本次提交的 `Frontend CI`、`Backend CI` 成功。分支推送只检查，镜像构建和生产部署跳过是正常现象。

## 2. 合并 main 并推送

```sh
git switch main
git pull --ff-only origin main
git merge --ff-only develop
git push origin main
```

`--ff-only` 拒绝存在分叉、无法快进的合并；遇到拒绝先检查分支历史，不改用强推。再次确认 `main` 上对应提交的前后端 CI 成功。

## 3. 创建并推送正式 Tag

先核对工作区、当前提交和已有远程标签：

```sh
git status
git log -1 --oneline
git ls-remote --tags --refs origin
```

确认位于已推送、检查通过的 `main`，工作区干净，且新版本未使用后，创建附注标签：

```sh
# 历史示例：下次执行时替换为新的版本号。
git tag -a v0.1.5 -m "Release v0.1.5"
git push origin v0.1.5
```

推送正式 Tag 会触发真实生产部署。已发布 Tag 不移动、不覆盖；修复工作流后应通过包含修复的新版本验证，重跑旧 Tag 仍使用旧提交中的工作流。

发布后可以切回日常开发分支；切换本地分支不影响远程流水线：

```sh
git switch develop
```

## 4. 检查流水线

打开该 Tag 对应的 Actions 运行，确认顺序完成：

1. `Frontend CI`、`Backend CI`：代码检查。
2. `Build and Push Docker Images`：版本与 main 历史归属校验、构建或复用镜像、推送 TCR。
3. `Deploy Production`：SSH 连接服务器、校验版本、拉取镜像、备份数据库、更新容器、检查健康及正式 HTTPS 接口。

展开 `Deploy to Ubuntu Server`，最后应看到 `生产部署成功：v0.1.5；记录：...`，或者同版本已成功部署且健康的提示。TCR 中出现版本标签只说明镜像已发布，不能单独证明服务器更新完成。

## 5. 在服务器确认运行版本

下面是 Ubuntu 服务器命令，不在本地 PowerShell 执行。不要输出或分享完整 `.env`。

```sh
# 第一列应是本次版本；后面是源码提交、前端摘要、后端摘要。
sudo cat /opt/maplehush/releases/last-success.tsv

# 两个版本均应是本次版本。
sudo grep -E '^(FRONTEND_VERSION|BACKEND_VERSION)=' \
  /opt/maplehush/config/.env

# 查看容器镜像与健康状态，人工运维也必须加载摘要锁文件。
sudo docker compose \
  --env-file /opt/maplehush/config/.env \
  -f /opt/maplehush/compose/compose.yaml \
  -f /opt/maplehush/config/image-lock.yaml \
  ps
```

前后端应运行且健康，显示的镜像摘要应与 `last-success.tsv` 一致。镜像显示 `仓库地址@sha256:...` 正常：流水线将 Tag 对应镜像的摘要写入 `image-lock.yaml`，固定实际运行内容；版本号仍保存在 `.env` 和成功记录中，不需要手动改回按 Tag 运行。

最后打开正式网站，验证登录、菜单和本次变更涉及的功能。容器健康不能替代业务验收。

## 发布失败时

先看 Actions 的失败步骤，再检查 `/opt/maplehush/releases/` 对应目录的备份和诊断记录。更新开始后的失败可能已影响容器和数据库；若存在 `deployment-pending`，先核查现场再决定继续或回退，不直接删除标记重跑，不盲目恢复数据库。

日常自动发布不需要手动修改服务器版本。接入自动部署后，手工改 `.env` 可能与成功记录或摘要锁不一致；不要混用早期单侧手动更新流程。服务器 Compose、Nginx 站点等宿主机文件不会由本流水线自动上传，修改这些文件需单独同步并验证。

## 部署脚本如何更新

脚本拆分后，Git 发布命令不变。`.github/workflows/ci.yml` 调用 `.github/scripts/` 中的版本校验、镜像检查和 SSH 交付脚本；部署 Job 从本次 Tag 提交检出 `deploy/server/deploy.sh`，核对上传文件摘要后保存在服务器 `/opt/maplehush/scripts/` 并执行。无需人工在服务器维护第二份 `deploy.sh`。

已有服务器目录、Secrets、成功记录和摘要锁继续沿用；首次发布包含重构的新 Tag 时，流水线准备 root 所有的 0700 脚本目录，原有其他脚本不删除。更新脚本本身仍需提交、合并 main 并使用新 Tag；重跑旧 Tag 不会使用新脚本。拆分后真实上传、Linux 权限和完整发布链路需通过新版本验证，不能仅凭本地回归通过认定服务器已迁移。
