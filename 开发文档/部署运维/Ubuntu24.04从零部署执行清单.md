# Ubuntu 24.04：从空服务器到测试、生产流水线发布

本清单是正式部署的执行入口；基础安装命令以[正式服务器手册](./正式服务器Docker部署.md)为准。最终目标是 Ubuntu 24.04 LTS amd64 上的测试、生产两套环境，由 GitHub Actions 构建并发布 Docker 镜像，服务器拉取指定镜像并通过 Compose 更新。

2026-10-27 用户确认最终采用流水线。此前“手动脚本是最终入口”的安排已调整：手工安装和源码构建作为首次演练，部署脚本作为后续流水线执行工具。完整环境约定与分阶段验收见[测试与生产流水线部署方案](./测试与生产流水线部署方案.md)。不引入 Jenkins，部署操作仍放在本目录，不混入产品功能任务拆解。

建议最终测试、生产各一台服务器；学习阶段可先在一台机器运行两套隔离 Compose。一个主域名下使用 `test-admin.example.com`、`admin.example.com` 两个子域名，分别配置 HTTPS。下文第 1～11 步先在测试环境完成并验收，再用生产参数重复必要的初始化步骤；正式服务器手册中的 prod 示例不能直接当成测试配置执行。

## 如何一起执行

1. 准备好服务器后，在对话中说“开始部署第 1 步”，提供该步骤需要的非秘密信息。
2. 每次只执行当前步骤。助手先核对前一步结果，再把示例替换为本机实际 IP、域名、路径和版本，给出命令。
3. 用户在指定终端执行，反馈文字输出；命令失败就停在当前步骤，不连续重装、删容器或删卷。
4. 确认成功标准后，把实际结果记入进度表，再进入下一步。未执行的步骤保持“未开始”。
5. 密码、私钥、JWT、OSS Key 不贴到聊天；在服务器受控文件或凭据管理中配置。

本清单现在仅代表执行安排，尚未在新的正式服务器上实施。本地虚拟机结果不直接勾选为正式服务器通过。

## 第 1 步：信息登记、连接服务器

**执行位置：** 本地 Windows PowerShell、服务器 SSH 终端。

需要提供或记录：

| 信息 | 填写值 |
| --- | --- |
| 云厂商及区域 | 待填写 |
| 测试 / 生产服务器公网 IPv4 | 分别填写；同机演练需明确标记 |
| 测试 / 生产域名 | `test-admin.example.com` / `admin.example.com`，替换实际值 |
| SSH 登录用户名及端口 | 待填写，不提供密码/私钥 |
| 维护人的公网来源 IP | 待核对，用于访问限制 |
| 证书续期通知邮箱 | 开始证书步骤时填写 |
| 代码仓库 | `https://github.com/maplehush/maple-hush-admin.git` |
| 发布分支 | 测试 `develop`；生产 `main` |

先通过 SSH 登录，再查看：

```sh
cat /etc/os-release
uname -m
free -h
df -h /
timedatectl
```

**成功标准：** Ubuntu 24.04（noble）、x86_64；主机、资源、剩余磁盘和时间状态明确，具备安装权限。

**失败处理：** 登录或系统不符时先处理，不继续安装。具体命令参考[系统检查](./正式服务器Docker部署.md#1-检查系统磁盘时间和网络)。

## 第 2 步：安全组、网络和域名

**执行位置：** 云控制台、DNS 管理后台、服务器终端。

- SSH 实际端口只允许维护来源，先验证不会失去管理访问。
- 域名 A 记录指向服务器公网 IPv4；如存在 AAAA，核对 IPv6 是否真实可达。
- 80 端口供证书验证和后续 HTTPS 跳转使用；443 在首次引导阶段限制为维护来源。
- 不公开 3306、6379、8080、8090；Docker 发布端口与主机防火墙一起核对。

**成功标准：** 外部 DNS 指向正确机器，SSH 正常，端口规则已记录。证书申请前再确认 80 的实际可达性。

**失败处理：** 先检查解析记录、TTL、云安全组及已有防火墙，不重置所有规则。参考[网络要求](./正式服务器Docker部署.md#1-检查系统磁盘时间和网络)。

## 第 3 步：软件源与基础工具

**执行位置：** 服务器运维终端。

- 核对 Ubuntu 24.04 的 `/etc/apt/sources.list.d/ubuntu.sources`。
- 云厂商已提供稳定内网源时保留；需要替换时按手册使用 TUNA 普通归档源，保留官方 security 源。
- 安装 CA、curl、GnuPG、Git、OpenSSL、Python 3、nano 和宿主机 Nginx。

**成功标准：** `apt-get update` 无签名或仓库错误；基础工具可用，`nginx -t` 通过，Nginx 服务已启动。

**失败处理：** 核对 noble、CA、网络与源文件格式，不关闭 TLS/签名校验。执行命令见[软件源与基础工具](./正式服务器Docker部署.md#2-ubuntu-软件源与基础工具)。

## 第 4 步：Docker 与 Compose

**执行位置：** 服务器运维终端。

- 通过已签名的 Docker CE apt 仓库安装 Engine、containerd、Buildx 和 Compose 插件。
- 设置 Docker 开机启动，记录实际版本。
- 不在宿主机安装项目的 Java、Node、MySQL 或 Redis。

验证：

```sh
docker version
docker info
docker buildx version
docker buildx ls
docker compose version
```

**成功标准：** Engine 正常，Compose 至少 2.24.4，使用 `docker compose` 插件命令。

**失败处理：** 查看 Docker 服务日志及包来源，不混装 docker.io/旧 docker-compose，不手工替换 runc。命令见[Docker 安装](./正式服务器Docker部署.md#3-安装-dockerbuildx-和-compose)。

## 第 5 步：目录与发布代码

**执行位置：** 服务器运维终端。

固定结构：

```text
/opt/maple-hush/
  maple-hush-admin/    产品仓库
  backups/            受控数据库备份
  releases/           发布记录与回退信息
/opt/maple-hush-secrets/prod/   生产密钥，独立于源码
```

首次按当前环境克隆：测试使用 develop，生产使用 main；正式手册提供 main 示例。核对：

```sh
cd /opt/maple-hush/maple-hush-admin
git branch --show-current
git status --short
git log -1 --oneline
```

**成功标准：** 当前环境分支正确，工作区干净，提交已在开发机提交推送。生产提交还须经过测试验收。全部 Compose 命令从产品仓库根执行。

**失败处理：** 检查 Git 网络或仓库访问；不把 token 写入 URL，不强制覆盖现有目录。命令见[部署工作区](./正式服务器Docker部署.md#5-建立干净的部署工作区)。

## 第 6 步：镜像与构建依赖源

**执行位置：** 服务器；需要企业镜像同步时，另使用能访问上游的构建机器。

- 先确认 Docker Hub 是否可用；受限时使用实际有权限管理的企业镜像仓库。
- 核对 MySQL、Redis、Maven、Java、Node、Nginx 六张基础镜像，以及 Dockerfile 解析器镜像。
- 在根 `.env` 配置实际 `*_IMAGE`、`DOCKERFILE_FRONTEND`、npm/Maven/运行镜像 apt 参数。
- 分别验证宿主机和容器网络。只有确实需要时才用 `BUILD_NETWORK=host`。

**成功标准：** 使用最终配置能拉取所需镜像，包源可达；不把公共示例仓库当成真实可用地址，不遗漏解析器。

**失败处理：** 区分镜像拉取、包下载与 BuildKit gRPC 异常，保留日志，不反复删缓存/删卷。完整分支步骤见[容器镜像供应](./正式服务器Docker部署.md#4-容器镜像从哪里拉)及[构建源配置](./正式服务器Docker部署.md#6-根-env-与构建依赖源)。

## 第 7 步：环境参数与七个文件密钥

**执行位置：** 服务器受控编辑器。

- 分别配置 test/prod、独立项目名/库名、回环入口、真实 HTTPS Origin、实际 OSS 参数。同机时生产 8090、测试 8091；具体对照见流水线方案。
- 生成独立随机 MySQL root、应用数据库、Redis、JWT 值，准备三个 OSS 凭据文件。
- 核对宿主机受控目录及容器内非 root 用户可读性；不提交真实 `.env` 和密钥。
- 首次空库引导开关在第 9 步受限访问窗口开启；正常运行保持关闭。

验证配置：

```sh
docker compose config --quiet
docker compose config --services
```

**成功标准：** 当前环境配置解析成功，仅四个服务，七个运行密钥路径正确。记录配置位置，不记录秘密内容。

**失败处理：** 逐个检查变量和文件，不通过 chmod 777 或开发默认密码解决。命令见[环境参数](./正式服务器Docker部署.md#6-根-env-与构建依赖源)及[生产密钥](./正式服务器Docker部署.md#7-创建生产文件密钥)。

## 第 8 步：域名、Nginx 与 HTTPS

**执行位置：** 服务器、浏览器；必要时操作 DNS 控制台。

1. 配置仅用于证书验证的临时 HTTP 站点。
2. 域名解析和 80 可达后，使用 Certbot webroot 签发证书，或接入已有受控证书。
3. 配置 80 跳转、443 HTTPS 与到 `127.0.0.1:8090` 的代理。
4. 检查 Nginx 配置并 reload，核对续期任务与重新加载 hook。

**成功标准：** `nginx -t` 通过，证书域名和链有效；续期验证通过。应用尚未启动时可以先出现上游 502，需在第 9 步后消失。

**失败处理：** 排查 DNS/AAAA/80/站点匹配及 CA 输出，不为上线关闭 Secure Cookie。命令见[HTTPS 完整步骤](./正式服务器Docker部署.md#8-域名nginx-与-https首次准备)。

## 第 9 步：首次构建与启动

**执行位置：** 服务器仓库根目录。

确认是空库且访问限于维护人员，再开启首次管理员引导并执行：

```sh
docker compose up -d --build --wait --wait-timeout 600
docker compose ps
curl -fsS http://127.0.0.1:8090/healthz
curl -fsS http://127.0.0.1:8090/api/auth/captcha
docker compose exec backend curl -fsS http://127.0.0.1:8080/actuator/health/readiness
```

**成功标准：** 四服务健康，Flyway 成功，前端到后端 API 链路正常；外部只有预期公开入口。

**失败处理：** 先收集当前构建或服务日志，定位具体阶段；不清空数据库、不增加 `down -v`。`--wait` 超时不会自动回滚。详见[首次启动](./正式服务器Docker部署.md#9-首次部署改密与关闭引导)。

## 第 10 步：首次改密、关闭引导与验收

**执行位置：** 浏览器和服务器终端。

- 通过真实 HTTPS 域名获取新验证码，完成初始管理员登录和强制改密，再重新登录。
- 关闭 `ADMIN_BOOTSTRAP_ENABLED`，用 `up -d --wait --wait-timeout 600` 应用配置。
- 验证工作台、权限、一次关键写入、退出和再次登录；验证会话刷新与 OSS 上传。
- 核对 prod 不公开 Knife4j/OpenAPI 和数据库端口。完成后再开放实际业务访问范围。

**成功标准：** 改密后账号可用、数据正常、引导关闭，功能验收结果明确。不能只凭容器 healthy 判定全部成功。

**失败处理：** 区分服务端登录失败与前端处理异常，不把重建容器当密码重置。未配置 OSS 的功能需明确保留待验收项，不能直接勾选完成。参考[首次验收](./正式服务器Docker部署.md#9-首次部署改密与关闭引导)。

## 第 11 步：备份恢复与一次手动更新

**执行位置：** 服务器仓库根目录；恢复只写入隔离库。

- 执行已有备份脚本，保存 SQL、校验值、Git/Flyway/镜像记录。
- 将备份恢复到新的隔离库，核对关键表和数据，不覆盖业务库；保留异机副本。
- 保留旧应用镜像和配置，确认 schema 兼容性，执行一次备份 → 拉取 → 构建 → 更新 → 健康检查 → 浏览器验收。
- 核对现有数据仍在，确认发布后排查入口、磁盘空间和回退资料可用。

**成功标准：** 备份非空且校验通过、隔离恢复有效、手动更新可重复执行。恢复过程和可能的数据损失窗口有记录。

**失败处理：** 备份失败不发布，恢复失败保留隔离现场；应用镜像回退不等于数据库回退，不自动改正式库。命令见[更新流程](./正式服务器Docker部署.md#10-以后每次更新)、[备份与恢复](../../deploy/ops/README.md#2-mysql-备份)及[隔离恢复](../../deploy/ops/README.md#3-校验与隔离恢复)。

## 第 12～15 步：接入最终流水线

按[测试与生产流水线部署方案](./测试与生产流水线部署方案.md)逐项实施。交付范围如下，当前均未实现：

- [ ] 第 12 步：两套环境隔离，镜像仓库、部署账号和 GitHub Environments 配置完成。
- [ ] 第 13 步：develop 检查通过后构建、推送镜像，自动发布测试环境；PR 检查不接触部署密钥。
- [ ] 第 14 步：main 对应已验收源码，人工确认后将同一镜像摘要发布生产；先备份、后更新、再检查。
- [ ] 第 15 步：验证并发、备份失败、拉取失败、健康超时、旧镜像回退及隔离数据库恢复。

最终服务器不再执行源码构建；部署脚本只接受受控环境、提交和镜像摘要，执行备份、拉取镜像、更新与健康检查。工作流、脚本和仅运行镜像的 Compose 配置需要后续交付，目前不能执行尚未创建的入口。原有 `up --build` 命令保留用于前面手工演练。

**成功标准：** develop 能自动更新测试环境；生产必须经人工确认，并部署已经验收的同一组镜像；失败返回非零、保留日志与备份，不自动恢复业务数据库。实际目标服务器演练通过后才能标记完成。
