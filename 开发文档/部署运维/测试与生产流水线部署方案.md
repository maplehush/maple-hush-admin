# 测试与生产流水线部署方案

> 更新：2026-10-27。本文记录用户确认的最终部署目标和实施顺序；当前仅完成方案整理，没有创建发布工作流、部署脚本、GitHub 环境或远程资源。

## 1. 最终目标与入口

基线为 Ubuntu 24.04 LTS amd64，GitHub Actions + 企业镜像仓库 + Docker Compose + 宿主机 Nginx。已有 `.github/workflows/ci.yml` 负责前后端检查，尚无镜像发布和远程部署。推荐使用实际可访问并有管理权限的阿里云 ACR 企业仓库；账户、区域、费用和 runner 网络可达性在实施时核定。不要把 Docker Hub 加速地址当成可推送的业务镜像仓库。

基础安装按[从零执行清单](./Ubuntu24.04从零部署执行清单.md)与[正式服务器手册](./正式服务器Docker部署.md)进行。手工源码构建是演练阶段，最终由 runner 构建，目标服务器只运行镜像。无需引入 Jenkins。

## 2. 环境与分支约定

| 配置 | 测试环境 | 生产环境 |
| --- | --- | --- |
| 域名示例 | test-admin.example.com | admin.example.com |
| 来源分支 | develop | main |
| Spring profile | test | prod |
| GitHub Environment | test | production |
| 发布触发 | develop 检查成功后自动 | main 与验收版本匹配，人工确认后发布 |
| Compose 项目名 | maple_hush_test | maple_hush_prod |
| 数据库名 | maple_hush_test | maple_hush_prod |
| Redis 前缀 | maple_hush_test | maple_hush_prod |
| 密钥目录示例 | /opt/maple-hush-secrets/test | /opt/maple-hush-secrets/prod |
| 同机演练的前端入口 | 127.0.0.1:8091 | 127.0.0.1:8090 |
| Origin 示例 | https://test-admin.example.com | https://admin.example.com |

一个主域名下配置两个子域名即可，分别设置 DNS、Nginx 站点和 HTTPS。建议最终各用一台服务器；学习时可以同机运行两套独立 Compose，使用不同源码/运行目录和环境文件。两个域名本身不提供数据或资源隔离。

每套分别运行 frontend/backend/mysql/redis；MySQL 存储卷、账号密码、Redis 实例和密码、JWT、OSS 权限与对象前缀、日志与备份都要独立。测试不使用生产数据和生产凭据。test 环境在线接口文档只向授权测试人员开放。

develop 允许领先 main，测试验收后再合并；不再要求每次开发提交都立即同步两个分支。main 禁止未经验证的直接发布。合并动作本身不等于完成生产发布。

## 3. 构建与版本晋级

1. PR 只做检查和测试，不读取部署密钥，不发布到服务器。
2. develop 检查成功后，在 runner 构建两张应用镜像并推送；记录源码提交、前后端镜像摘要、构建结果和迁移版本。
3. 测试环境按这一组明确摘要部署并验收。标签用于辨识，实际部署固定 `image@sha256:...`，不能依赖会变化的 latest/local。
4. 验收时冻结发布清单；合并 main 后检查生产源码与该清单源码树一致。合并提交 SHA 可能不同，不能仅比较 SHA 就误判源码相同。
5. 人工确认生产发布后，提升同一组已验收的镜像摘要，不重新构建。如果 main 内容与验收源码不同，停止生产发布，重新构建并回到测试验收。
6. runner 构建镜像应支持两套环境共用，域名和后端地址由部署配置/Nginx 注入；实施前核对现有前端构建不包含必须按环境固化的参数。

服务器部署顺序：校验发布清单与环境 → 获取部署锁 → 记录旧镜像与配置 → 数据库备份并校验 → 拉取目标镜像 → Compose 更新并等待健康 → readiness、前端/API 与外部 HTTPS 检查 → 保存发布记录。

保留 `--wait --wait-timeout 600` 作为初始等待配置，超时返回失败，不代表自动回滚。部署需要另一个“只运行镜像”的 Compose 入口，不能把现有带 build 的配置直接称为最终流水线交付。

## 4. 权限和连接

- runner 使用镜像推送凭据；服务器只配镜像拉取凭据，按环境分开。
- 部署通过专用 SSH 账号和固定命令入口，校验服务器 host key，不禁用主机身份检查。具有 Docker 控制权的账号按高权限账号管理。
- 运行密钥留在服务器受控文件；GitHub 环境只保存必要部署凭据，不将密码、私钥写入镜像、Git、发布清单或日志。
- 不开放数据库和 Redis 端口；宿主机 Nginx 暴露 80/443，应用入口仅绑定回环。
- 公网不可达的本地虚拟机不能假设 GitHub 托管 runner 能直接 SSH。学习时使用有受控网络通路的专用 self-hosted runner；限制其运行可信分支，不能让公开 PR 在持有部署权限的 runner 执行。
- 正式环境按实际网络选择托管 runner 或专用构建 runner，不在生产业务主机执行不可信构建。每个环境限制并发发布为 1，已开始的生产发布不被新提交随意取消。
- GitHub production 配置审批及允许分支；如套餐不支持所需保护，先采用受控的人工触发和权限限制并明确能力差异，不能把手动按钮等同于独立审批。

## 5. 分阶段实施与验收

这些步骤对应执行清单第 12～15 步，尚待实施；基础安装完成后逐项交付。

### 第 12 步：环境和镜像仓库

- [ ] 登记两套 IP、域名、路径、端口、项目名和密钥目录；核对资源与数据隔离。
- [ ] 配置两个 Nginx HTTPS 入口，分别验收登录、刷新、权限与上传。
- [ ] 建立镜像仓库、受限推送/拉取账号及 GitHub Environments；验证 runner 到仓库、到服务器的连接。
- [ ] 交付只运行镜像的 Compose 配置与发布清单格式；记录镜像保留策略，确保可回退。

成功标准：两套环境不共享凭据和业务卷；目标机器能拉取指定摘要，不能误更新另一环境。

### 第 13 步：测试流水线

- [ ] 复用现有检查门槛，检查失败不进入发布。
- [ ] 交付 GitHub Actions 镜像构建及测试发布工作流，第三方 Action 固定到审核过的提交。
- [ ] 交付受控部署脚本，检查环境、并发锁、备份、拉取、更新、健康检查和发布记录。
- [ ] 提交 develop 后验证自动更新测试环境；检查日志不包含密钥，PR 无部署权限。

成功标准：源码提交、镜像摘要与实际测试实例可对应，重复部署不清空数据、不重复初始化管理员。

### 第 14 步：生产流水线

- [ ] 交付验收清单晋级、main 源码对应校验、审批/人工确认与生产发布流程。
- [ ] 生产只拉取已经测试验收的两张镜像，执行备份并核对结果。
- [ ] 验证生产健康、公开 HTTPS/API 和浏览器关键业务；记录审批人及实际部署版本。

成功标准：未验收或摘要被替换时拒绝发布；生产审批前不执行生产备份或更新，批准后才取得所需环境凭据。

### 第 15 步：失败与恢复

- [ ] 模拟检查失败、备份失败、镜像拉取失败和健康超时，确认非零退出、日志和发布记录完整。
- [ ] 验证两个发布并发时按环境串行，测试发布不阻断或覆盖生产。
- [ ] 用兼容数据库结构的上一版镜像演练回退；保留当前故障证据。
- [ ] 将备份恢复到隔离库验证，再验证异机备份可用；不自动覆盖生产数据库。

成功标准：失败停止且可定位；镜像回退和数据库恢复分别有经过验证的步骤。Flyway/schema 变更不兼容时禁止盲目回退应用。首次安装、业务验收和恢复结果必须来自实际目标服务器，文档、语法检查和容器 healthy 不能替代。

## 6. 当前交付边界

本轮只更新部署文档和执行安排。GitHub Actions 构建/发布工作流、部署脚本、仅运行镜像的 Compose、服务器、域名、证书、仓库权限与生产审批均未配置或验证；现有手工部署命令仍可用于演练。后续按阶段实施，不预先把待办记为完成。
