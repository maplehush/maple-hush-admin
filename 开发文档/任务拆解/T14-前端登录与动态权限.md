# T14 前端登录与动态权限

**前置**：T06 和 T01 的前端基线。**范围**：`apps/web-antdv-next` 登录、会话与路由；只建立系统菜单所需的最小页面组件入口，七个系统页面的真实查询与写操作留给 T15。

## 实施

- [x] 登录页保留用户名、密码，加入服务端图形验证码；移除演示账号选择、自动填入演示密码与 `SliderCaptcha`。
- [x] 对接正常登录/待改密两种互斥响应；待改密只进专用页面，成功后回登录页。实现 access 过期刷新、退出与 401/403 处理，不把待改密凭据存为普通 access。按 T01 契约通过 `GET /api/auth/csrf` 获取 token；刷新和退出同时携带 refresh Cookie 与 `X-XSRF-TOKEN`，退出可附带当前 access token，但 access 已过期时仍须能通过 refresh Cookie 与 CSRF 完成退出和本地状态清理。登录或退出后重新获取 CSRF 凭据；CSRF 失败的 403 不进入 refresh 循环。同一页面的并发 401 只触发一次 refresh；同源多标签页协调刷新并分发新 access token，协调失败时要求重新登录，不重复使用旧 refresh。
- [x] 使用 `accessMode: 'backend'` 获取 `/api/menu/all` 与 `/api/auth/codes`；开发代理和生产路径仅有一个 `/api` 前缀，关闭 mock 调用。为后续从 Playground 移植的用户、角色、菜单、部门页面先建立相同的 `system/*/list.vue` 入口；字典与两种日志页面按 T03 最终种子路径新增 `list.vue`。这些入口在本任务只保证路由可加载，明确显示功能仍待 T15 完成，不提供虚假的查询数据、操作按钮或成功提示；T15 在相同路径实现真实页面。

## 本轮实施安排（2026-10-14）

1. 对照锁定的产品前端实际源码，先写会话协调单元测试并观察失败；保留原 workspace，关闭目标应用 mock，代理保留唯一 /api 前缀。
2. 认证传输单独实现图形验证码、两类登录、首次改密、CSRF、原始字符串 refresh 和退出；专用改密凭据仅保存在内存，不放普通 access 或浏览器存储。
3. 会话协调使用同源 Web Locks 串行化登录/刷新/退出，同页 Promise 合并、共享短期 access 状态与 BroadcastChannel/storage 事件分发；每请求记录会话 epoch，禁止旧账号请求在新账号登录后重放。协调失效/不确定的刷新失败需重新登录，不自动重试旧 refresh；明确的 503 保留会话以供稍后重试。
4. 请求客户端只对业务 401 刷新并至多重试一次，403 不刷新。跨标签页登录/退出会清旧资料、权限和动态路由；本地退出不依赖未过期 access。
5. 使用后端菜单模式，七个系统组件仅显示待开放说明。工作台作为所有已登录用户共用的基础入口，不接受角色授权；个人入口与 403 仍是受保护静态路由。个人中心正式表单仍留 T16，T14 不暴露假成功提示。直接访问未授权系统路径显示 403。
6. 用独立 MySQL 库/Redis 前缀与独立端口启动真实后端/前端做浏览器验收，不改现有用户账号口令、不停止用户正在运行的 8080/5999 服务。验证验证码/首次改密、正常登录、同页并发、多标签页、CSRF、退出和不同权限路由；日期墙钟值按 yyyy-MM-dd HH:mm:ss 处理，不当 UTC 二次转换。
7. 执行目标 typecheck/build、单元和浏览器测试、独立审查，同步任务/架构/契约与交接，提交本轮。未执行的实际场景明确记录。

裁定：短期 access 可按既有 Vben 模式持久化，协调状态只含 access/epoch/revision，不保存 refresh、密码或首次改密凭据。旧 Vben 演示认证状态不作为平台登录态继承。保留用户对 preferences.ts 的版权修改与 backend/pom.xml 修改，提交时只纳入本轮偏好字段变更。下一任务 T15 由用户另行发起。


## 执行记录（2026-10-15）

### 已交付

- 目标应用关闭 Nitro mock；开发代理直达 `http://127.0.0.1:8080`，原样保留 `/api`。`VITE_API_PROXY_TARGET` 仅用于隔离联调；`VITE_CACHE_DIR` 可隔离并行 Vite 的依赖缓存。生产调用固定同源 `/api`。
- 登录只保留用户名、密码、图片验证码，去掉演示账号、自动密码和滑块；验证码失败后换新。Vben 上游缓存 Login，故 `onActivated` 也会清密码并重新获取验证码，避免首次改密返回时继续使用已消费的验证码。
- 正常 access 与首次改密凭据互斥；专用改密凭据只留在内存。改密成功回登录页，用新密码重新登录。身份资料保留后端字段含义，不从 user/info 构造 token。
- 独立认证传输处理验证码、登录、首次改密、CSRF、refresh 原始 JSON 字符串和退出；登录/退出后主动续取 CSRF，每次 refresh/logout 前重新获取并带 Cookie 与 `X-XSRF-TOKEN`。退出不依赖未过期 access。后端访问 `/auth/codes` 时可能清理 CSRF Cookie，客户端不依赖长期缓存的 CSRF 值。
- Web Locks 串行化认证 Cookie 操作，同页 Promise 合并刷新，共享短期 access/epoch/revision，并用 BroadcastChannel/storage 分发。旧账号请求不能在新账号下重放；退出获锁后重新检查 epoch。登录响应后续 CSRF 失败等不确定结果会使旧会话失效，避免新 Cookie 搭配旧身份。存储写失败清本地状态并通知其他页面，刷新协调不可用时要求重新登录。明确的刷新 503 保留会话；403 不进入刷新循环。
- 固定后端权限模式，恢复会话时重取本人信息、权限码与菜单；清理身份时从干净副本重建基础路由，移除上一账号动态路由。工作台、个人入口、403 为受保护静态路由。后端七个系统组件全部可加载，只显示 T15 待开放提示。个人表单仍属 T16，未提前实现 CRUD、按钮或假成功提示。
- 增加日期墙钟解析工具及独立测试页，不将后端 `yyyy-MM-dd HH:mm:ss` 当 UTC 再加八小时。测试页位于 `__tests__/e2e`，不注册产品路由、不进入生产入口。
