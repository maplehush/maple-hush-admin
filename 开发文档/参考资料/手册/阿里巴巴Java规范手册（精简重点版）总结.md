## 图片中的注释规则

| 条目 | 图片标记 | 要点 |
| --- | --- | --- |
| 1 | 强制 | 类、属性和方法的文档注释使用 JavaDoc 的 `/** ... */` 形式，便于 IDE 提示与文档生成；不要用普通 `//` 代替文档注释。 |
| 2 | 强制 | 抽象方法和接口方法说明功能，以及参数、返回值、异常、实现约束或调用注意事项。 |
| 3 | 强制 | 类注释记录创建者与创建日期。这是原手册要求，是否采用仍由本项目规范决定。 |
| 4 | 强制 | 方法内部单行注释放在被说明语句的上一行，使用 `//`；多行说明用 `/* ... */`，注意与代码对齐。 |
| 5 | 强制 | 枚举成员要说明每个值的用途。 |
| 6 | 推荐 | 中文能把问题说清时使用中文；专有名词和技术关键词保留原文。 |
| 7 | 推荐 | 参数、返回值、异常和核心逻辑变化时，同步修改相关注释。 |
| 8 | 参考 | 谨慎保留注释掉的旧代码；将来要恢复时说明原因，永久不用就删除，由版本库保存历史。 |
| 9 | 参考 | 注释应准确表达设计意图和业务含义，帮助后续维护者理解代码背后的原因。 |
| 10 | 参考 | 优先写清晰的名称和结构；对已自解释的语句避免重复注释，以免形成维护负担。 |
| 11 | 参考 | 可见部分要求特殊标记注明负责人和时间，并及时处理；图片后续文字被裁切。 |

## 对本项目有用的落点

- 为跨模块公开接口、复杂业务方法和关键实体字段写有内容的 JavaDoc；参数、返回值或异常的约定需要写清，不生成空标签。
- 行内注释解释权限边界、并发控制、事务和审计等**为什么这样处理**；简单的 CRUD 步骤靠命名和代码结构表达。
- 修改代码时同步核对注释；不在仓库里留无说明的大段注释代码。
- 原手册“所有类写创建者和日期”与当前[后端开发规范](../../开发规范/后端开发规范.md)的“不写自动生成的作者、日期”不同。本文只记录来源内容，不自动改变现行规则；若要改项目约定，需要单独统一文档。
