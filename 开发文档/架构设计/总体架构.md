## 1. 已确定的方案

| 项目 | 决定 |
| --- | --- |
| 架构 | 模块化单体；业务模块统一按功能分包，包内使用 Controller → Service → Mapper 三层；业务 Service 统一使用 `service/I...Service` 接口和 `service/impl/...ServiceImpl` 实现，调用方注入接口 |
| 部署 | 一个 Spring Boot 进程、一个可执行 Jar；暂不拆微服务 |
| Maven 模块 | `admin-base-core`、`admin-system-api`、`admin-system-biz`、`admin-system-start` |
| 技术栈 | Java 21、Spring Boot 4.1.x、Spring Web MVC、Spring Security、MyBatis-Plus、MySQL 8.4 LTS、Flyway、Redis（Spring Data Redis/Lettuce）；公共工具采用 Lombok 与 Hutool 的 `core`、`captcha` 模块 |
| 默认数据库名 | `maple_hush_admin`；部署时通过配置指定，迁移脚本不写死库名 |
| 认证 | 用户名、密码和服务端图形验证码登录；JWT access token + 服务端保存哈希的轮换 refresh token |
| 文件存储 | 阿里云 OSS；首版头像放独立的公共读 Bucket，由后端上传，数据库保存长期可访问的 HTTPS URL |
| 命名 | Maven `groupId=com.maplehush`；Java 包前缀 `com.maplehush.admin`；系统管理类名用 `Sys`、部门用 `Dept`；实体不加 `Entity`，入参 DTO 与出参 VO 带后缀；权限码全小写 |
| 首版范围 | 认证；用户、角色、菜单、部门、字典、日志六个系统功能领域（日志分登录日志、操作日志两个页面）；当前用户资料、本人改密和 OSS 头像上传 |

模块职责、Java 目录和依赖方向见[后端项目结构](./后端项目结构.md)。本模板借鉴 [JeecgBoot 的 Maven 模块划分](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/pom.xml)，接口契约以 Vben 当前代码为准。Spring Boot 4 选用 `mybatis-plus-spring-boot4-starter`，不混用 Boot 3 starter 或单独的 MyBatis starter；Spring Boot 4.1 与 MyBatis-Plus、OpenAPI 组件的组合仍需通过启动、分页、事务和序列化集成测试后锁定版本。[MyBatis-Plus 官方安装说明](https://baomidou.com/getting-started/install/)。

T02 后按用户要求加入 Lombok `1.18.48`、Hutool `5.8.48`：Lombok 作为编译期依赖，由 Maven Compiler 显式配置注解处理器；`hutool-core` 放公共模块，`hutool-captcha` 放系统业务模块供 T04 生成图形验证码。Hutool 只负责所选工具功能，不替代 Spring MVC、Jackson、Bean Validation、Spring Security、Redis 或 MyBatis-Plus；验证码答案的一次性校验与限流仍按 Redis 设计实现。其他工具包在有具体功能时再引入，避免提前增加重复能力。[Lombok Maven 指南](https://projectlombok.org/setup/maven)、[Hutool 官方站](https://www.hutool.cn/)。

## 2. Vben 联调契约

T15 已把 Playground 的用户、角色、菜单、部门四套页面实际移动到 `web-antdv-next`，并新增字典和两个日志页面，均已接入真实后端；其他 Playground 演示继续保留为参考，不作为部署产物。

首版左侧有“系统管理”一级目录，包含用户、角色、菜单、部门、字典五个页面及“日志管理”子目录（登录日志、操作日志），共七个页面；不增加岗位、参数或代码生成。`web-antdv-next` 的“个人中心”通过头像下拉进入，不算系统管理页面；其基本资料与修改本人密码需要真实后端接口。当前演示页面存在 mock 角色选项和只弹出“修改成功”的改密操作，正式交付时须替换，不能让用户自行改角色。

普通接口统一返回 `com.maplehush.admin.common.api.Result<T>`，JSON 形状为：

```json
{"code":0,"data":{"items":[],"total":0},"error":null,"message":"ok"}
```

[参考提交的目标应用请求拦截器](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/web-antdv-next/src/api/request.ts)以 `code=0` 判断成功，并把响应中的 `data` 交给业务调用方；成功包装参照 [Vben mock 响应](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/backend-mock/utils/response.ts)使用 `code/data/error/message`，其中 `error=null`。Java 类型仍叫 `Result<T>`，不使用 JeecgBoot 的 `result` 字段。请求 `traceId` 放响应头并写入日志，不增加菜单 JSON 字段；T01 必须以实际前端代码核对。

| 前端调用 | 对外路径 | 关键约定 |
| --- | --- | --- |
| 获取登录验证码 | `GET /api/auth/captcha` | 匿名访问；`data.captchaId`、`data.imageBase64`（原始 PNG Base64），禁止缓存 |
| 获取 CSRF 凭据 | `GET /api/auth/csrf` | 匿名访问；返回 `data.token` 并设置同源 CSRF Cookie，供携带 refresh Cookie 的刷新和退出请求使用，禁止缓存 |
| 登录 | `POST /api/auth/login` | `LoginDTO` 包含 `username/password/captchaId/captchaCode`；正常登录返回 `data.passwordChangeRequired=false`、`data.accessToken` 并设置 HttpOnly refresh Cookie；待改密时仅返回 `data.passwordChangeRequired=true` 和短时效 `data.passwordChangeToken`，两种凭据互斥 |
| 首次或重置后改密 | `PUT /api/auth/initial-password` | 只接受专用改密凭据与新密码；成功后凭据失效，前端返回登录页重新登录 |
| 当前用户 | `GET /api/user/info` | `userId` 为字符串，并返回 `username/realName/avatar/roles/introduction` |
| 本人资料 | `PUT /api/user/profile` | 首版只允许本人修改 `realName` 和 `introduction`；`username/roles` 只读，不接收账号状态等授权字段 |
| 本人改密 | `PUT /api/user/password` | 个人中心由当前用户输入旧密码和新密码；校验后更新密码哈希、递增 `authVersion`、撤销本人所有会话；前端清理登录态并跳转登录页，用新密码重新登录 |
| 本人头像 | `POST /api/user/avatar` | 登录后上传受限图片到阿里云 OSS，服务端绑定当前用户；返回长期可访问的头像 URL |
| 权限码 | `GET /api/auth/codes` | `data` 为当前用户的权限码数组 |
| 当前菜单 | `GET /api/menu/all` | `data` 为可访问的 Vben `RouteRecordStringComponent[]` 路由树，不是数据库菜单记录 |
| 刷新 | `POST /api/auth/refresh` | 携带 Cookie；**直接返回 token 字符串**，当前前端从原始 `resp.data` 读取 |
| 退出 | `POST /api/auth/logout` | 携带 refresh Cookie 与 CSRF 请求头；按 refresh 会话撤销当前令牌族并清除 Cookie，当前 access token 随即失效；access 已过期也可退出 |

认证路径与返回读取方式已按 T0 锁定的实际前端提交核对；[旧参考提交的 auth API](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/web-antdv-next/src/api/core/auth.ts)只保留历史依据。验证码、CSRF 凭据和头像是本项目新增契约，需同步修改前端。Vben 参考实现的刷新和退出均通过 `baseRequestClient` 携带 Cookie，本项目须在这两项调用补充 `X-XSRF-TOKEN`，退出可附带当前 access token，但服务端不得依赖它定位会话族；有效 refresh Cookie、CSRF 凭据与来源校验足以退出，过期 access 不阻止清除 Cookie。T01 要交付基于实际提交的前后端接口契约清单：逐接口记录调用位置、方法与路径、请求 DTO、成功/失败响应示例、HTTP 状态与业务码、所需权限码，并特别核对刷新接口的原始字符串、字符串 ID、分页、时间格式、CSRF 获取与请求头。后续任务以该清单和真实源码联调，接口改动同步更新清单。普通接口用统一响应体，刷新接口是特例。未认证或 access token 失效返回 HTTP 401，已认证但权限不足返回 403；CSRF 缺失或无效返回 HTTP 403 和稳定业务码，前端不对此发起 refresh。请求使用 `Authorization: Bearer <token>`。开发代理和生产网关均只保留一个 `/api` 前缀。refresh Cookie 在生产设为 `HttpOnly`、`Secure`、`SameSite=Lax`、host-only，`Path=/api/auth`。CSRF 凭据由 `GET /api/auth/csrf` 签发，服务端保存预期值于同源 `HttpOnly` Cookie，前端从响应 `data.token` 取得提交值，在 refresh/logout 请求头发送 `X-XSRF-TOKEN`；CSRF Cookie 同样限制为 host-only、`Secure`、`SameSite=Lax`、`Path=/api/auth`，不作为认证凭据。登录、刷新、退出还须校验请求来源；登录或退出导致 CSRF 凭据重置后，前端重新获取，不能继续提交旧值。不得因使用 JWT 就全局关闭 CSRF；T05 已按实际 Spring Security 7.1.1 验证 XOR 提交值、请求头校验与 Cookie 生命周期。[Spring Security CSRF 说明](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

参考提交的目标应用[登录页](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/web-antdv-next/src/views/_core/authentication/login.vue)包含账号选择、自动填入演示密码和 `SliderCaptcha`，只适用于演示；T01 核对实际版本中的对应实现。正式登录页保留用户名与密码输入，增加“验证码输入框 + 可点击刷新的图片”；图片由后端生成、校验由后端完成，不以滑块组件的前端布尔值作为凭据。交互参考 [JeecgBoot 登录页](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecgboot-vue3/src/views/sys/login/LoginForm.vue)，视觉仍沿用 Vben。

### 系统管理接口

| 功能 | 参考路径 | 关键数据 |
| --- | --- | --- |
| 用户 | `/api/system/user/list`、`/api/system/user`、`/api/system/user/{id}`、`POST /api/system/user/{id}/reset-password` | 分页 `items/total`；账号 `username` 与展示名 `name` 分开，`name` 对应数据库 `real_name`；支持角色和部门；创建或重置后临时密码为 `12345678`，首次登录强制修改 |
| 角色 | `/api/system/role/list`、`/api/system/role`、`/api/system/role/{id}`、`/api/system/role/{id}/status` | `permissions` 为菜单树节点 ID，角色另有稳定编码；状态使用独立 PUT，仅修改状态字段 |
| 菜单 | `/api/system/menu/list`、`/api/system/menu/name-exists`、`/api/system/menu/path-exists` | 完整管理树，含按钮节点；字段匹配 Playground 的 `SystemMenu` 类型；类型 `catalog/menu/embedded/link/button` |
| 部门 | `/api/system/dept/list`、`/api/system/dept`、`/api/system/dept/{id}` | `pid/children` 树结构 |
| 字典 | 新增 `/api/system/dict/**` | 字典类型与字典项的管理及查询；字典项返回可选 `color`（`#RRGGBB`）供状态标签展示 |

前四组暂依据参考提交 `playground/src/api/system` 的[用户](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/playground/src/api/system/user.ts)、[角色](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/playground/src/api/system/role.ts)、[菜单](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/playground/src/api/system/menu.ts)和[部门](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/playground/src/api/system/dept.ts)封装。移植时先核对实际提交的目录、列表 TypeScript 类型与分页体，再补齐用户登录账号、角色编码等字段。

动态路由采用 `accessMode: 'backend'`。`/api/system/menu/list` 返回完整管理树；`/api/menu/all` 只返回当前用户可访问的路由节点，按钮节点不进入路由树。`/api/auth/codes` 汇总当前用户获授且有效的菜单节点和按钮节点上的非空 `auth_code`。页面节点可以使用 `auth_code` 表示进入页面所需的查询权限，例如用户页面对应 `system:user:list`；创建、修改等操作码放在其按钮子节点。T03 按 T01 核对的目标路径种入菜单；T06 验证路由数据形状，T14 建立与系统路由匹配的最小页面组件并验证加载，T15 完成七个页面的真实交互。最终每个路由 `component` 都须匹配目标应用真实存在的 `src/views` 文件；不要同时注册相同路径的静态和动态路由。[Vben 路由转换代码](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f)。

登录默认地址 `/dashboard/workspace` 由正常动态菜单承载：“概览”目录 `/dashboard` 下的“工作台”页面 `workspace`，组件键 `/dashboard/workspace/index`。V8 为所有既有角色授予目录和工作台页面；角色创建、更新时服务端自动保留工作台授权，角色授权表仍是唯一菜单来源。前端不再静态注册同路径的工作台路由，避免静态与动态路由重复；组件位于 `frontend/apps/web-antdv-next/src/views/dashboard/workspace/index.vue`。

两种菜单响应分别对齐上游的 [当前用户菜单 mock](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/backend-mock/api/menu/all.ts)、[菜单管理 mock](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/backend-mock/api/system/menu/list.ts)及其 [mock 数据](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/apps/backend-mock/utils/mock-data.ts)。上游 `/menu/all` 的示例数据是 Dashboard/Demos；下面的 `System` 样例沿用其响应形状，路由名和路径则参考 Playground 系统路由。上游管理 mock 的系统树只列出部分页面，本项目扩展为七页：

- `GET /api/menu/all` 的 `data` 为路由树，节点使用 `name/path/component?/redirect?/meta/children?`。根路由 `path` 为 `/system`，子路由为 `user` 等相对路径；`component` 是无 `.vue` 后缀的页面键，例如 `/system/user/list`。不返回数据库 `id/pid/type/status/authCode`，也不返回按钮节点。示例仅展示一条页面：

  ```json
  [{"name":"System","path":"/system","meta":{"title":"系统管理","icon":"lucide:settings-2","order":10},"children":[{"name":"SystemUser","path":"user","component":"/system/user/list","meta":{"title":"用户管理","order":10}}]}]
  ```

- `GET /api/system/menu/list` 的 `data` 为管理树，节点包含 `id/pid/name/type/status/path?/component?/authCode?/meta/children?`；按钮保留在 `children` 中，`path` 和 `component` 可缺省。对齐 Playground 菜单表单与 mock 的系统菜单示例，管理树中的路由 `path` 使用完整地址 `/system/user`，`component` 仍为 `/system/user/list`，`authCode` 使用本项目的小写权限码。`id/pid` 对外用字符串，与前端 [SystemMenu 类型](https://github.com/vbenjs/vue-vben-admin/blob/d27a5b8a0c2972a10d583a7050fcb889766ff83f/playground/src/api/system/menu.ts)一致。示例同样只展示一条页面和一个按钮：


## 3. 认证与权限

登录验证码获取和登录接口加入 Spring Security 匿名白名单；本人头像上传仅允许已登录用户操作。`imageBase64` 传输原始 PNG Base64，前端显示时加 `data:image/png;base64,` 前缀。验证码保存在 Redis，后端进程重启不会单独使其失效；过期、原子消费或 Redis 数据清空后才失效，前端重新获取即可。

登录依次执行请求限流、验证码校验、密码哈希与账号状态校验，并记录结果；按账号和可信客户端 IP 限制连续失败尝试，采用短时冷却，避免永久锁定账号。验证码生成返回随机 `captchaId` 与 Base64 图片，答案仅存 Redis，带 2 分钟 TTL；登录时原子取出并删除，正确或错误都只能尝试一次，过期及输错后前端重新获取。验证码获取和登录限流计数也保存在 Redis 并设置 TTL，图片与响应禁止缓存；验证码错误用 HTTP 400 和稳定业务码，不泄露账号是否存在。Redis 不可用时不得绕过验证码和限流。图形验证码是登录防刷的补充，不能代替账号/IP 限流。JeecgBoot 的[登录控制器](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-module-system/jeecg-system-biz/src/main/java/org/jeecg/modules/system/controller/LoginController.java)可参考其图形验证码流程，本项目不照搬 URL 和日志实现。具体职责、失效及故障处理见[Redis 与环境配置设计](./Redis与环境配置.md)。

短期 access token 只保存身份、令牌族 ID 和授权版本，不保存菜单或完整权限列表。T04 的正常登录一次性签发初始 access token 和 refresh Cookie，并将当前用户最小快照写入 Redis；T05 在此基础上实现 refresh 原子轮换、退出撤销和清理。每次受保护请求除校验 JWT 与 MySQL 中的账号状态、`authVersion` 外，还须确认其令牌族仍有有效会话；Redis 快照只加速当前用户资料读取，缓存缺失时从 MySQL 重建。刷新只轮换族内令牌，不使已签发且未过期的 access 因旧 refresh 已使用而失效。退出撤销当前令牌族，因而当前 access 在下一次请求失效；本人改密或管理员重置目标用户密码则撤销其所有令牌族并递增 `authVersion`，同时清理快照。refresh token 使用高熵随机值，数据库仅存哈希；同一令牌只能轮换一次，已使用令牌再次提交时拒绝请求、撤销该令牌族并记录安全事件。T14 前端对同一页面的并发 401 合并为一次刷新，并协调同源多标签页的刷新及新 access token 分发；协调失败时要求重新登录，不能重复提交旧 refresh。用户角色或角色菜单关联变化时递增受影响用户的 `authVersion`，请求校验该版本，使旧令牌失效；菜单定义与当前有效权限由后端每个请求从数据库计算，菜单维护后前端重建当前会话的动态路由。首版从数据库加载有效权限，同一请求内复用判定结果；先为授权关系建索引并观察查询耗时，再决定是否增加权限结果缓存。[OWASP 登录防刷建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

首版默认 access token 有效期 15 分钟；refresh 令牌族从正常登录起最多有效 7 天，轮换时新令牌继承该族原定到期时间，不无限续期。refresh Cookie 的到期时间与 MySQL 中的令牌族到期时间一致。已使用的旧 refresh 哈希记录至少保留到该族到期，才能在有效期内识别重放；过期后按可配置留存期清理。并发轮换须在 MySQL 事务中锁定旧记录、只允许一个后继令牌生效。具体测试由 T05 覆盖。

T05 已落地：初始签发与轮换统一先锁用户再锁会话，refresh 会话的 `auth_version` 必须等于当前用户版本。正常轮换保留旧哈希，重放撤销整族并在独立事务记录安全事件；退出由 refresh 哈希定位令牌族，允许 access 已过期。V3 增加会话签发版本并回填此前记录。清理任务默认每小时运行一次，仅删除族到期后超过 7 天留存期的记录；`AUTH_SESSION_RETENTION_DAYS` 与 `AUTH_SESSION_CLEANUP_DELAY_MS` 可覆盖，撤销本身不会使有效期内的重放证据被提前删除。

### 初始密码、强制改密与重置

本项目按**内部企业后台、由管理员创建账号并及时交付**的使用方式，统一将 `12345678` 作为新建用户、用户列表管理员重置密码和首次超级管理员的临时密码；数据库只保存加盐哈希，不保存明文。新建与用户列表重置时设置 `sys_user.must_change_password=true`；管理员重置还要递增目标用户的 `authVersion` 并撤销其全部 refresh 会话，目标用户旧 access 在下一次请求失效，前端清理登录态并跳转登录页。执行重置的管理员仍留在用户管理页；如果重置的是管理员自己的密码，其本人也退出。个人中心的本人改密是另一个入口：当前用户先输入旧密码和新密码，成功后本人退出并直接用新密码重新登录，不经过临时密码或再次强制改密。固定临时密码只用于上述受控入口，不能作为改密后的正式密码。部署后先完成超级管理员首次改密，再创建其他账号；新账号及时交付本人，继续保留登录限流和审计。

新密码由前后端同时提示和校验，**后端以至少 8 个字符为底线，且 UTF-8 不超过 BCrypt 的 72 字节上限**，拒绝 `12345678` 等常见/已泄露密码以及与当前密码相同的值；不强制“大写 + 小写 + 数字 + 特殊字符”的组合规则，允许较长口令和密码管理器填入。由于图形验证码不是第二认证因素，本项目的用户名密码登录仍属于单因素认证；现行 NIST/OWASP 指南对单因素密码推荐的最低长度是 15，8 位只是本项目目前接受的产品下限，前端应建议用户使用更长的密码。[NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)、[OWASP 密码强度建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)。

首次登录或管理员重置后的登录仍须校验用户名、密码和图形验证码。若 `must_change_password=true`，后端不发普通 access token/refresh Cookie，只发 5 分钟有效、仅能调用 `PUT /api/auth/initial-password` 的专用改密凭据；其他业务 API 一律拒绝。改密成功时原子清除标记、更新密码哈希、递增 `authVersion`、撤销已有会话，使该凭据不可再用；前端清理临时状态并跳转登录页，由用户以新密码重新登录。正常已登录用户在“个人中心”改密也需提交旧密码；成功后递增 `authVersion`、撤销全部 refresh 会话并回登录页。改密与重置后重新认证符合 [OWASP 会话管理建议](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)。

授权源只有一处：`sys_user_role` 与 `sys_role_menu` 连接用户、角色和 `sys_menu` 节点。角色表单提交节点 ID；页面节点可带查询 `auth_code`，按钮节点必须带操作 `auth_code`。权限码统一为小写 `system:resource:action`，例如 `system:user:list`、`system:user:create`、`system:role:grant`。授予页面时须包含其目录祖先以形成可用路由；授予按钮必须同时授予所属页面，不能留下孤立按钮授权。移除页面授权时一并移除其下按钮授权；仅目录祖先不会额外授予接口权限。路由树只带可见页面及必要祖先，权限码只从获授且启用的节点生成，不因补齐目录而扩权。前端菜单、按钮码和后端接口权限从同一授权关系生成。

T06 已实现三个当前用户查询接口和方法授权底座：`AccessTokenFilter` 逐请求核对 MySQL 账号、版本与令牌族，再将有效权限码放入 Spring Security authorities，并把同次查询的用户/角色/菜单结果保存为认证上下文。`PermissionGraph` 从启用角色直接获授的页面与按钮计算有效码；停用祖先、断链、循环及孤立按钮不生效。路由仅补齐目录祖先，目录不产生接口权限；根目录缺省组件使用目标应用已有的 `BasicLayout`。路由扩展元数据按 Vben 实际 `RouteMeta` 类型过滤，不下发 `authority/ignoreAccess/loaded` 或任意 JSON 字段；`title/icon/order` 由专用列生成。内部层级目前为目录 → 页面 → 按钮，T07 写接口须验证同样的层级约束。

`IAuthorizationChangeService` 必须在业务事务内调用：`roleChanged` 递增该角色关联用户版本，`usersChanged` 递增指定用户版本；调用方须在删除关联前捕获受影响用户，或在同一事务删除前调用。版本更新回滚时不清理缓存，提交后清理失败只记录告警，旧 JWT 仍被 MySQL 拒绝。`profileChanged` 在提交后清理本人资料快照。菜单定义变更不递增会话版本；受保护请求每次从数据库重算菜单和权限，前端菜单维护后刷新当前路由。T07～T10 的真实管理写接口按授权影响接入这些方法；T11 字典变更不改变授权版本或用户会话。

管理 API 使用 Spring Security `@PreAuthorize("hasAuthority('system:user:list')")` 等声明，`/api/**` 默认要求登录。无身份返回 401，无权限返回 403。Service 对角色分配、角色授权等高风险变更再核对操作者可授予的范围；用户修改角色需 `system:user:assign-role`，角色修改菜单授权需 `system:role:grant`。部门 `deptId` 目前用于归属和列表筛选，不代表数据范围授权。[Spring Security 方法授权](https://docs.spring.io/spring-security/reference/servlet/authorization/method-security.html)。

管理列表按实际 Playground 表格调用接收 `page=1`、`pageSize=20`，并限制 `page>=1`、`1<=pageSize<=100`；响应仍为 `items/total`。日期范围筛选接收 `startTime/endTime` 的 `YYYY-MM-DD` 日期字符串，后端按 `Asia/Shanghai` 整日范围解释，结束日包含全天；接口返回的时间点仍使用 `yyyy-MM-dd HH:mm:ss`。批量 ID 操作首版最多接收 100 个 ID。排序字段与方向只能从每个接口显式允许的集合中选择，不能把前端提交的字段名直接拼入 SQL。Controller 校验格式与数量，Service 校验角色分配、菜单层级等依赖当前数据库状态的规则。

首次部署先创建默认名为 `maple_hush_admin` 的空数据库及受限应用账号；数据库初始不需要手工建表或导入演示数据。应用启动时由 Flyway 在该库创建 11 张表、迁移记录表，并种入内置 `super_admin` 角色、基础菜单和按钮节点，以及对应的 `sys_role_menu` 授权关系；迁移脚本不写用户或密码。仅当 `sys_user` 为空且部署者显式设置 `ADMIN_BOOTSTRAP_ENABLED=true` 时，`AdminBootstrapRunner` 从运行环境读取管理员账号，用临时密码 `12345678` 创建首个超级管理员、存储哈希并标记 `must_change_password=true`。首次改密完成后将引导开关改为 `false`；此后若 `sys_user` 意外变为空，应用应明确拒绝启动，不自动重建默认账号。不开放公开的初始化接口。生产库不预置演示用户、演示部门、字典项或日志；这些数据由管理员按实际业务维护或由系统运行产生。多套实例共用同一 MySQL 服务时，各实例须使用独立数据库和账号。

`super_admin` 是唯一的内置超级管理员角色，系统完成首次引导后始终只有一个账号持有该角色。角色不可删除、停用或通过普通角色表单改授权；其授权仍以 `sys_role_menu` 为准，新增菜单或按钮节点时同步授予该角色。首次引导负责创建唯一持有者；普通用户创建、编辑、批量操作和角色分配接口一律不得授予或移除 `super_admin`，后端也必须拒绝绕过页面的请求。唯一超级管理员账号不得通过用户管理接口删除、停用、重置密码或改动角色；本人可在个人中心修改资料和密码。识别依据是内置角色关联，不依赖固定用户 ID 或用户名；首次引导之后启动时校验该角色恰有一条用户关联且关联用户处于启用状态，异常时拒绝启动并由运维核查数据，不通过普通业务接口自动补建。非超管只能分配自己持有的非内置角色，角色授权只能选择自己现有有效权限范围内的菜单节点；拒绝越权请求，不能仅靠前端隐藏选项。用户角色或角色菜单变更时，在同一业务事务内更新受影响用户的 `authVersion`。

唯一超管若遗失密码或账号被错误停用，不能通过公开接口或重新打开首次引导开关补建第二个超管。T04 实现只在维护模式运行的离线恢复命令，常规启动因超管停用而拒绝时仍可独立运行：由有数据库维护权限的运维人员核验目标账号与备份状态，生成一次性随机临时密码，更新该账号密码哈希、启用状态与 `must_change_password`，递增 `authVersion` 并撤销其所有 refresh 会话；不改变超管角色关联。恢复操作写入独立运维记录，不输出密码到应用日志；T21 在隔离环境演练。此紧急路径不属于用户列表重置流程。

T06 的 `@OperationLog` 放在公共模块，切面与 Mapper/Service 放在 `system-biz/log`。切面在事务拦截器外层：独立业务事务完成后写审计，加入调用方事务时等待其完成，再按提交/回滚结果写入 `REQUIRES_NEW` 审计事务。日志摘要仅为固定结果文本，不序列化入参、返回值或异常消息；目标 ID 只从明确指定的正整数 `Long` 参数提取。请求路径保存实际请求 URI，包含路径实参，不包含查询串；路径参数不得设计为承载密码或 token 等凭据。历史审计中的路由模板保留原值。审计插入及提交失败记录错误日志和进程内失败计数，不改变已经提交的业务结果。T07 起接入具体管理写操作，T12 已实现查询与保留清理。

T07 已实现菜单管理树、增改删和名称/完整路径查重。输入按 Playground 表单接受 `pid/name/type/path/component/redirect/authCode/status/meta`，`meta.title/icon/order` 映射独立列；其他元数据按 T06 白名单及类型校验，不接受 `authority/ignoreAccess/query` 等任意扩展。`status` 缺省 1、`meta.order` 缺省 0，`meta.title` 必填；已知可选文本的空字符串/NULL 视为清空；修改为全量表单更新，可空列显式写 NULL，防止旧组件、图标或元数据残留。ID 对外为正整数字符串，空/`0` 父 ID 表示根节点；路由名采用 100 字符内的英文字母开头标识。

菜单层级限定目录 → 目录/页面 → 按钮，路由节点最大 32 层。完整路径只接受 `/segment` 形式的静态地址，段由字母、数字、下划线、连字符组成；不接受尾斜杠、动态参数、查询串、空段或路径穿越。子地址必须在父目录完整路径下，入库时去掉父前缀。目录移动会重新验证所有后代完整路径，忽略路径大小写查重。重定向仅指向现有数据库菜单路径，拒绝循环与删除仍被引用的目标。删除不级联下级；无下级和重定向依赖后，删除角色关联及节点，并使原授权失效。

菜单写事务先锁唯一 `super_admin` 角色行，串行验证跨层级路径，随后复核操作者 MySQL 状态和授权版本，避免请求等待期间沿用旧权限。新增节点在同一事务授予内置角色；增改删调用 T06 版本辅助服务、提交后清理快照并写实际操作审计。菜单变更保守使所有已分配角色用户的旧令牌失效，包括操作者。普通管理员仍需对应接口操作码，且只能操作本人有效权限及可见父节点范围；移动、修改或删除现有节点还须覆盖其整棵子树，不能用改码扩大授权。T09 涉及角色菜单关联并发写入时须与该菜单写锁顺序协调。

普通页面组件键由业务模块资源 `menu-components.txt` 登记，不接受任意文件路径或 `.vue` 后缀。系统键为七个 V2 预留页面、工作台、个人中心、关于及 Antdv 演示；Analytics 组件键暂留清单供未来页面接入。七个系统组件已在 T14 建入口、T15 接真实管理交互，新增真实页面时同步清单。目录组件缺省，根可指定 `BasicLayout`；内嵌页面固定 `IFrameView` 并要求 `meta.iframeSrc`；外链要求 `meta.link` 且不配置组件/重定向。外链表单不展示路由地址，上级目录可选；后端用菜单唯一名称自动生成内部路由路径，实际跳转目标只使用 `meta.link`。外部地址只接受无用户名密码的 HTTP(S) URL；服务端不抓取这些地址。

T08 已实现部门树与增改删，列表为完整树数组，不分页；同级按 `sort ASC,id ASC` 排序，包含停用节点。根节点对外 `pid="0"`，数据库 `parent_id=NULL`，叶子返回 `children=[]`，ID 为字符串，时间沿用东八区秒级格式。表单采用 `pid/name/sort/status/remark`，`name` 非空且至多 100 字符、备注至多 500 字符，排序缺省 0、状态缺省 1，更新是全量表单；空父 ID/`0` 表示移回根，空备注显式写 NULL。同名部门允许，数据库未设计名称唯一索引。

部门写事务沿用菜单的唯一内置角色行作为首版结构变更互斥锁，空树创建和并发父级调整均先串行校验整树；拒绝不存在父级、自身/后代为父级以及超过 32 层的树。等待写锁后复核操作者 MySQL 状态和授权版本。删除还锁目标部门行，并拒绝任何子部门或关联用户（含停用用户）；并发分配用户以 MySQL 外键最终兜底，关联冲突返回 409，不级联删除、不自动迁移用户。

四个部门 API 使用已有的 `system:dept:list/create/update/delete` 权限码，关键写操作接入 T06 的提交后/失败独立审计。部门状态、层级变化不改变账号或角色权限，不递增用户授权版本，不清理当前用户最小快照；`deptId` 仍只是归属和后续用户列表筛选字段，不引入岗位或数据范围授权。

T09 已实现角色分页、详情、创建、修改与删除，授权通过创建/修改中的 `permissions` 菜单 ID 数组提交，不另设重复授权入口。列表按 `id ASC` 稳定分页，`page>=1`、`1<=pageSize<=100`，支持名称模糊、0/1 状态和东八区整日日期范围筛选；响应 `items/total`，分页内菜单关联批量读取。`roleCode` 创建必填，为英文字母开头的小写字母/数字/下划线、至多 64 字符，创建后不可改；`name` 映射 `role_name`，非空且至多 100，备注至多 500。内置标记始终由后端生成，普通接口拒绝创建 `super_admin`，也拒绝修改或删除任何内置角色。

权限输入最多 100 个正整数菜单 ID，去重后规范化：授予页面补齐目录祖先，新增孤立按钮拒绝；若取消原页面但表单仍回传其原按钮，则同时清理这些旧按钮。路由层级与 T07 的最多 32 层路由（按钮另计一层）一致。创建时省略/null 权限为空，修改时省略/null 权限保留旧值，显式空数组清空。创建状态缺省 1，修改省略/null 状态保留旧状态；名称、备注为表单属性，空备注清除。属性修改不会隐式启用停用角色。

新增实际授权或修改授权需额外 `system:role:grant`；停用角色改为启用同样需要该权限，并复核其最终权限集合，防止通过启用持有中的高权限角色越权。非超管只可授予自己当前有效的页面/目录/按钮节点；页面按有效路由可见性、按钮按直接获授 ID 和有效操作码双重限定，不从单独目录推导页面权利。超管可保留/授予已存在的停用节点，但节点在启用前不产生有效权限；节点启用仍由 T07 递增受影响版本。

所有角色写事务先持有与菜单/部门相同的内置角色行互斥锁，再复核操作者状态及授权版本。菜单授权或角色状态变化在同一事务递增全部持有者版本，提交后清快照；只改名称/备注或回传同一规范化授权集合不撤销会话。删除角色先捕获原持有者并递增版本，再删除用户/菜单关联和角色，禁止遗漏原成员。缓存清理失败只告警，MySQL 版本仍拒绝旧 access/refresh；受影响操作者也需重新登录。关键写入接入 T06 操作审计，不保存权限请求体。T10 的用户角色分配必须遵守同一锁顺序并检查本人可分配角色范围，本步不提供给用户分配角色的写接口。

## 4. 数据与日志

### 时间与时区

本项目参照 JeecgBoot 的接口时间格式与东八区配置：业务、审计和刷新会话时间列使用 MySQL `DATETIME`，**精确到秒**；后端统一以 `Asia/Shanghai` 生成和解释这些值，Java 21 实体优先用 `LocalDateTime` 映射。`DATETIME` 不携带时区，也不会自动转换成 UTC；应用、JDBC 连接和 MySQL 会话必须使用一致的东八区约定。`CURRENT_TIMESTAMP` 取决于数据库会话时区。T03 已用 JDBC 的 `connectionTimeZone=%2B08:00&forceConnectionTimeZoneToSession=true` 在本机 MySQL 8.0.24 验证 `@@session.time_zone=+08:00`、数据库默认值和应用读写；本机未加载命名时区表，直接设置 `Asia/Shanghai` 会报 1298。目标 MySQL 8.4 与浏览器往返仍须后续复验。[MySQL 时间类型说明](https://dev.mysql.com/doc/refman/8.4/en/datetime.html)、[JeecgBoot 配置](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-module-system/jeecg-system-start/src/main/resources/application-dev.yml)。

管理接口的时间字符串统一为 `yyyy-MM-dd HH:mm:ss`，例如 `2026-10-10 12:00:00`，其含义固定为 `Asia/Shanghai` 本地时间；后端须为 `LocalDateTime` 显式配置 JSON 序列化和反序列化格式，不能只设置传统 `Date` 的全局格式。不附加 `Z`，前端也不能把它当 UTC 再加八小时。T01 按实际拉取的 Vben 版本核对日期组件和解析方式。对接外部系统时在边界显式转换时区，避免把无偏移量的本地字符串当作跨系统绝对时间点；JWT 过期时间仍使用绝对时间戳，与上述数据库字段格式区分。秒级时间可能并列，日志分页和排序用 `(create_time, id)` 保证稳定顺序。

### 阿里云 OSS 文件上传

首版头像文件上限为 2 MiB，仅接受 JPEG、PNG、WebP；后端校验实际图片内容，不只相信扩展名或客户端声明的 MIME 类型。

首版开放与系统功能相关的头像上传和统一公开图片上传，不增加文件管理菜单。`POST /api/user/avatar` 从当前登录身份确定用户，后端校验文件大小、实际内容类型与允许的图片格式，生成不可预测的 Object Key 后使用 OSS Java SDK 上传；上传成功后按受控的公开访问域名拼出 HTTPS URL，写入 `sys_user.avatar_url`。`GET /api/user/info` 直接把该字段作为 `avatar` 返回，不保存带过期签名参数的 URL。更新头像时，服务端仅从已配置的头像域名和路径前缀下的旧 URL 提取 Object Key 并清理旧对象；数据库写入失败时清理新对象，清理失败记录并纳入运维补偿。用户资料接口不接受客户端任意头像 URL。以后若更换公开域名或 Bucket，需要迁移已存 URL；新增电商模块可复用 OSS 存储能力，但商品图片与私有附件分别决定访问权限，不沿用头像的公共读设置。[阿里云 OSS Java SDK V2](https://help.aliyun.com/zh/oss/developer-reference/oss-sdk-for-java-2-0)、[OSS Bucket ACL](https://help.aliyun.com/zh/oss/user-guide/oss-bucket-acl)。

头像使用独立的公共读 Bucket，任何获得头像 URL 的人都能读取图片，因此只允许存放适合公开展示的头像；写入和删除仍仅授权后端，不启用公共写。将来的私有附件使用私有 Bucket 和临时签名 URL。所有访问使用 HTTPS；应用优先使用运行环境提供的 RAM 角色凭证，其他环境使用受控注入的最小权限 RAM 凭证，绝不把长期 AccessKey 交给浏览器、放进镜像或提交仓库。用户提供的北京地域、`maple-hush` Bucket、公开访问域名和 `vben-admin-img/` 前缀按[环境配置设计](./Redis与环境配置.md#oss-头像配置)记录；T13 核对该 Bucket 是否满足独立公共读头像用途及 SDK 实际连接方式。前端只持有业务接口地址与头像 URL，不配置 `VITE_OSS_*`。Compose 不启动本地 OSS 容器。首版小文件经后端上传，未来大文件或高流量场景再评估短时凭证或服务端签名直传。[阿里云 OSS 凭证与权限说明](https://help.aliyun.com/zh/oss/developer-reference/oss-sdk-for-java-2-0)、[服务端签名直传](https://help.aliyun.com/zh/oss/user-guide/obtain-signature-information-from-the-server-and-upload-data-to-oss)。

| 数据 | 表 |
| --- | --- |
| 用户与组织 | `sys_user`、`sys_dept` |
| 角色与菜单 | `sys_role`、`sys_user_role`、`sys_menu`、`sys_role_menu` |
| 字典 | `sys_dict_type`、`sys_dict_item` |
| 会话 | `auth_refresh_session` |
| 日志 | `sys_login_log`、`sys_operation_log` |

`sys_menu` 保存路由与按钮节点；`sys_role_menu` 保存角色勾选的节点 ID。刷新会话表保存 token 哈希、用户、签发时 `authVersion`、令牌族、有效期和撤销状态；认证模块定期清理超过留存期的过期或已撤销会话，不另建通用任务平台。字典项在同一类型下的 `value` 唯一；可选 `color` 使用 `#RRGGBB` 格式，只用于页面状态标签的展示，与字典项启停 `status` 无关。11 张表的逐字段说明见[数据库表结构](./数据库表结构.md)；初始化设计输入为[第一份：建库建表 SQL 草案](../任务拆解/T03-01-建库建表草案.sql)和[第二份：系统基础数据 SQL 草案](../任务拆解/T03-02-系统基础数据草案.sql)。T03 已按实际前端路由复核并落为后端工程 [Flyway V1](../../backend/admin-system-start/src/main/resources/db/migration/V1__create_system_tables.sql) 和 [Flyway V2](../../backend/admin-system-start/src/main/resources/db/migration/V2__seed_system_data.sql)，由 Flyway 执行，不手工执行草案。V2 只预置内置角色、七个系统页面、操作按钮及其授权关系，不预置管理员账号、密码、业务部门或演示日志。

表结构统一使用小写 snake_case。可修改的系统主表默认包含 `id`、`create_time`、`update_time`；仅追加的日志表至少包含 `id`、`create_time`，会话表另外记录过期及撤销时间。`admin-base-core` 提供只声明 `createTime`、`updateTime` 的抽象 `BaseEntity`；首版 `SysDept`、`SysUser`、`SysRole`、`SysMenu`、`SysDictType`、`SysDictItem` 继承它，各实体自行声明主键。只有 `create_time` 的关联、会话和日志实体自行声明该字段，不为继承而增加数据库不存在的 `update_time`。父类字段标记 MyBatis-Plus 自动填充，由 `TimestampMetaObjectHandler` 在常规实体写入时填充东八区秒级时间；SQL 中的 `CURRENT_TIMESTAMP` 为未显式提供时间列的插入提供默认值，`ON UPDATE CURRENT_TIMESTAMP` 处理未显式设置 `update_time` 的数据库更新。使用不触发自动填充的 Wrapper 更新或自写 SQL 时，必须明确更新时间策略，T03 验证各路径不产生时间偏移。是否使用逻辑删除由具体表的恢复需求决定，不预设所有表都有删除标记。建表草案暂定有符号 `BIGINT` 主键并映射 Java `Long`，API 中的用户 ID 仍按 Vben 契约序列化为字符串；T03 在真实 MySQL 验证后定稿。

| 表 | 首版数据库约束与查询索引 |
| --- | --- |
| `sys_user` | `username` 唯一；`real_name` 对应 Vben 的 `name/realName`；`password` 只存不可逆哈希；`introduction` 供本人编辑，`remark` 供管理员备注；`avatar_url` 保存头像 HTTPS URL；`must_change_password` 标记临时密码待修改 |
| `sys_role` | 稳定角色编码 `role_code` 唯一；内置 `super_admin` 编码不可变 |
| `sys_dict_type`、`sys_dict_item` | 字典类型 `dict_code` 唯一；字典项 `(dict_type_id, value)` 唯一 |
| `sys_user_role`、`sys_role_menu` | 分别约束 `(user_id, role_id)`、`(role_id, menu_id)` 唯一；`sys_user_role` 另建按 `role_id` 查受影响用户的索引 |
| `auth_refresh_session` | token 哈希唯一；按用户和过期时间查询、清理所需索引由真实查询计划确认 |

以上约束由 MySQL 唯一索引兜底，Service 仍负责给出可理解的冲突提示。`sys_menu.title`、`icon`、`sort` 分别是路由元数据 `title`、`icon`、`order` 的权威来源；`meta_json` 只保存其他受白名单约束的 Vben 元数据，组装路由时由这些显式列覆盖同名 JSON 键，避免两份值冲突。菜单根节点 `path` 使用绝对路径，子节点使用相对路径；`path` 在同一父节点下唯一，根节点的 `NULL parent_id` 通过索引表达式归一化后参与查重。Service 还须校验父子路径拼接后的完整访问地址不冲突；按钮节点不占用路径。T03 用真实 MySQL 验证该索引，并在 T01 用实际前端路由复核。字典项同一类型至多一个 `is_default=1`，Service 在修改默认项时锁定对应字典类型行并在同一事务内切换，防止并发产生两个默认项。删除普通用户时先撤销并清理其刷新会话、删除用户角色关联，再删除用户；登录和操作日志保留账号快照。删除角色或菜单时先处理授权关联，再执行删除与 `authVersion` 失效。唯一超级管理员账号和内置角色不进入普通删除流程。不照搬旧手册“禁用所有外键”“最多 JOIN 三表”之类的绝对规则，外键和查询写法依据事务边界、维护成本及真实 MySQL 查询计划决定。

`sys_login_log` 记录登录成功、失败（含验证码错误）、受限尝试和退出；失败时用户 ID 可为空。`sys_operation_log` 记录密码重置、账号状态、角色授权、菜单与字典修改等关键操作及结果。前者由认证 Service 写入；后者的 `@OperationLog` 切面、写入 Service 和事务边界在 T06 落地，使 T07 起每项管理写操作都能实际留痕；T12 已完成两个日志页面所需的查询、脱敏复核和保留清理。审计摘要脱敏，不保存密码、验证码及答案、token 或完整敏感请求体。成功审计在业务事务提交后以新事务写入，失败审计也以独立事务写入；日志落库失败须记录错误并触发监控，不默认回滚已成功的业务操作。首版不引入 MQ 或无持久化保障的异步队列。[Spring 事务事件说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)、[OWASP 日志建议](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)。

## T12 日志查询与保留清理

登录与操作审计沿用 T04～T11 的写入链路；T12 实现两个独立权限的只读分页接口与显式 VO。分页使用 MyBatis-Plus Lambda 条件，排序仅接受 id/createTime；日期边界为东八区，账号沿用审计快照，不联表改写历史。操作摘要在写入和读取时均限定为固定结果；审计写失败仍不改变业务结果，错误日志只记事件、traceId、计数、异常类别，避免数据库异常带出字段值。登录与操作审计各有进程内 failureCount，日志清理也记录失败计数，重启会归零；运维通过 ERROR 日志接告警，不新增公开计数端点。

| 配置项 | 环境变量 | 默认值 | 行为 |
| --- | --- | --- | --- |
| maple-hush.log.login-retention-days | LOG_LOGIN_RETENTION_DAYS | 90 | 登录/退出/刷新失败日志保留天数，1～3650 |
| maple-hush.log.operation-retention-days | LOG_OPERATION_RETENTION_DAYS | 180 | 关键操作日志保留天数，1～3650 |
| maple-hush.log.cleanup-enabled | LOG_CLEANUP_ENABLED | true | false 时停止清理，不影响记录与查询 |
| maple-hush.log.cleanup-delay-ms | LOG_CLEANUP_DELAY_MS | 3600000 | 首次延时及后续固定间隔，单位毫秒，部署应配置正值 |

保留天数为可调整的产品运行默认值，按部署环境需要覆盖。清理取东八区当前秒减对应天数，只删除 create_time 严格早于截止点的记录；等于截止点的保留。每表每轮最多 10 批、每批 1000，按 create_time/id 索引顺序删除，每批单独提交。某表失败记录安全错误事件后继续清理另一表，下轮调度重试剩余记录；日志查询和清理不产生操作审计，防止日志自身放大。

使用已有 `(create_time,id)` 索引与 V1/V2/V3，不新增依赖、迁移、缓存、通用调度平台或对外删除/导出接口。MySQL 8.4 与 Docker 运维告警联通仍在后续部署任务验收；本轮以本机 MySQL/Redis 的真实集成测试验证。接口字段详见[T12 日志契约](../接口契约/前后端接口契约.md#t12-日志接口实施细节)。

## T13 本人资料、改密与 OSS 头像

本人资料、本人改密、头像上传三个接口已落地，分别只改姓名/简介、保存新密码哈希、绑定后端生成的长期公开 URL。普通登录用户可操作自己，不需要用户管理权限；写入时锁用户行复核账号状态与 authVersion。改密沿用统一 PasswordPolicy，补 UTF-8 72 字节上限，与既有 BCrypt 能力一致；Redis 限制本人改密每 5 分钟 5 次，成功撤销本人全部会话并清 Cookie，其他用户不受影响。

头像校验实际格式与尺寸后重新编码 PNG，最大 2 MiB，移除元数据并以随机名称保存。使用 OSS SDK V2 0.6.0 和 WebP ImageIO 3.15.3，SDK 基础能力位于 common/storage；本人身份和对象目录由 user 模块约束。上传先于短数据库事务，事务内复核身份、保存 URL 并安排快照失效；失败清新对象、成功提交后清旧对象。受控 URL 提取规则与错误码详见[T13 契约](../接口契约/前后端接口契约.md#t13-本人资料改密与头像实施细节)。

SDK 客户端延迟初始化，共享 HTTPS 连接，连接超时 5 秒、读写超时 15 秒、最多两次尝试；缺少后端凭据只影响头像上传。上传要求 Bucket 为 public-read，拒绝 private/public-read-write，不修改 Bucket 或 Object ACL；头像对象继承 Bucket ACL，最小权限包括 GetBucketAcl 与所配置前缀 PutObject/DeleteObject。公开读和匿名写保护的实际结果仍由用户后续上传验收。

数据库或 PUT 失败后补偿新对象，替换成功后清旧对象；清理异常只记录安全随机 Object Key、traceId 及进程内计数，供运维按 Bucket/Key 重试删除，重试前须确认已不被 sys_user.avatar_url 引用。此类日志须接入部署期告警/留存，首版不额外建立通用对象管理或任务平台。更换域名/前缀后，旧 URL 不自动跨边界删除，需人工迁移。

资料/头像修改不递增授权版本，当前用户快照读取还会比对 MySQL 的姓名、简介、头像与账号，防止删除失败或旧快照回填返回陈旧资料。T13 未新增数据库迁移、角色或菜单节点；前端个人中心的真实表单/改密跳转仍属 T16。

## T13 补充：统一上传能力

系统统一文件 HTTP 入口位于 `admin-system-biz/system/file`，底层复用 `admin-base-core/common/storage`。`POST /api/files/upload` 当前按公开图片白名单接收 JPEG/PNG/WebP，实际解码并转 PNG；以后按业务扩展类型和访问策略。它只生成公开素材和短期绑定标识，不修改任何用户资料。本人头像入口继续负责上传并立即更新本人。

### T20 根部署编排落地

根 [Compose](../../docker-compose.yml)通过 include 和小范围覆盖文件复用独立配置，要求 Compose 2.24.4+；为避免两种模式的相对路径歧义，根模式显式使用仓库根作为 project_directory，并覆盖两个构建 context 和 Redis 脚本路径。根环境统一从仓库根解析密钥目录，include 不读取子项目 .env；前端 upstream 固定为内部 http://backend:8080，后端及数据服务不发布宿主机端口。公开 HTTPS 由已有前端 TLS 网关承担，不新增第五个容器服务。

根 frontend 单侧命令不带起 backend，backend 单侧命令带起 MySQL/Redis；整体部署仍需后端 readiness 与 API 成功才算可用。已完成配置核对，缺少 Docker 引擎/域名证书，真实整体和单侧部署、持久化及 HTTPS 登录尚未验收；见 [T20 记录](../任务拆解/T20-仓库根目录一键部署.md#执行记录2026-10-19)。
