# 后端项目结构

本页只说明后端目录、依赖和新增业务模块规则。总体方案与 Vben 接口契约见[总体架构](./总体架构.md)。Maven `groupId` 为 `com.maplehush`，Java 包前缀为 `com.maplehush.admin`。

## 1. 模块职责

| 模块 | 职责 |
| --- | --- |
| `admin-base-core` | 公共响应、异常、实体时间基类、常量、工具、JWT 基础能力、Redis 公共配置、操作审计注解、MyBatis-Plus 配置和可复用的阿里云 OSS 存储能力 |
| `admin-system-api` | 当前用户、权限判断、部门查询等内部 Java 契约 |
| `admin-system-biz` | 认证（含图形验证码和强制改密）、用户（含 OSS 头像）、角色、菜单、部门、字典、日志及 HTTP 接口 |
| `admin-system-start` | 唯一启动类、环境配置、Flyway 和集成测试；唯一可执行 Jar |

这是**四个 Maven 子模块、一个 Spring Boot 进程**。`admin-system-biz` 和以后新增的业务模块按功能分包，包内统一为 Controller → Service → Mapper；`base-core` 和 `start` 承担公共技术与装配职责。[JeecgBoot 的 base-core、system-api、system-biz、system-start](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/pom.xml)是模块划分参考。

`common` 与 `config` 是 `admin-base-core` 内的 Java 包，不是额外 Maven 模块。`common/constant`、`util`、`annotation` 等均有首版用途；系统专属权限码留在 `admin-system-biz`。`common/entity/BaseEntity` 仅复用 `createTime`、`updateTime`；六个含这两列的系统主表实体继承它，主键仍由各实体声明。只有 `create_time` 的关联、会话和日志实体不继承它。系统管理资源统一以 `Sys` 开头，部门统一用 `Dept`：如 `sys_dept` ↔ `SysDept`、`SysDeptMapper`、`SysDeptService`、`SysDeptController`。实体类放 `entity` 包，类名不加 `Entity` 后缀，参照 JeecgBoot 的 [`entity/SysUser.java`](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-module-system/jeecg-system-biz/src/main/java/org/jeecg/modules/system/entity/SysUser.java)。`Sys` 是 Java 类名约定，包名与接口路径仍为 `dept`；认证和当前用户能力保持 `Auth...`、`CurrentUser...` 命名。接口入参放 `dto` 包，以 `DTO` 结尾，如 `LoginDTO`、`SysUserSaveDTO`，不叠加 `Request` 后缀；面向前端的出参放 `vo` 包，以 `VO` 结尾，如 `CurrentUserVO`；跨模块 API 数据对象也以 `DTO` 结尾，不复用 HTTP 的 VO。`Result<T>`、`PageResult<T>` 是公共响应容器，不按业务 VO 命名。借鉴 JeecgBoot 的 [`AutoLogAspect`](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-boot-base-core/src/main/java/org/jeecg/common/aspect/AutoLogAspect.java) 采集关键操作，但切面实现在 `admin-system-biz/log`，直接调用日志 Service；字典翻译和数据权限切面不进入当前范围。

验证码能力放 `system-biz/auth`：`AuthController` 提供 `GET /api/auth/captcha`，`CaptchaService` 用 Redis 保存 2 分钟答案并原子消费，`LoginDTO` 带 `captchaId/captchaCode`。登录限流和当前用户最小快照也由 `system-biz/auth` 实现，公共 Redis 连接、序列化与键前缀配置放 `admin-base-core/config`；不新建验证码表或 Maven 模块。四个配置文件及职责见[Redis 与环境配置设计](./Redis与环境配置.md)。`admin-base-core/common/storage` 只封装 OSS Java SDK、配置、上传、删除、公开 URL 拼接和私有对象签名读取，不判断某个用户能否修改头像；`system-biz/user` 负责文件校验、当前用户绑定、将头像公开 HTTPS URL 写入 `sys_user.avatar_url`，以及从受控 URL 提取 Key 清理旧对象。以后 `admin-mall-biz` 可复用同一存储能力，在自己的业务接口落实商品图片等权限和限制，不依赖 `system-biz` 的上传 Controller。

密码规则和临时密码的哈希处理在 `system-biz/auth/service/PasswordService` 统一实现：创建用户、管理员重置和首次超级管理员引导均使用约定的临时密码 `12345678`，正式改密仍校验新密码规则并禁止继续使用该值。`SysUser.mustChangePassword` 对应 `sys_user.must_change_password`。`AuthService` 在待改密状态只签发专用短期凭据，由 `PasswordChangeTokenService` 验证其类型、有效期和授权版本；`SecurityConfiguration` 确保该凭据不能调用普通业务接口。`SysUserService` 在创建、重置和改密时负责更新用户标记、授权版本与会话，重置他人密码不会让操作管理员退出。创建/重置响应不返回密码明文，用户列表、详情和日志也不包含密码。`AdminBootstrapRunner` 仅在空库且 `ADMIN_BOOTSTRAP_ENABLED=true` 时创建首个超管。

## 3. 依赖与调用规则

```text
admin-base-core ────────┐
                        ├──> admin-system-biz ──> admin-system-start
admin-system-api ───────┘
```

- `admin-system-biz` 依赖 `admin-base-core` 和 `admin-system-api`；`admin-system-start` 装配业务模块。`admin-system-api` 只放跨模块需要的内部查询接口与只读 DTO，不放业务实体或写入接口；同一 Maven 构建内同步修改契约与实现。
- `base-core` 提供 JWT 校验、通用响应和 `@OperationLog` 注解，不查询系统表。`system-biz/auth/security/SystemPrincipalService` 查询用户状态与权限，`system-biz/log/aspect/OperationLogAspect` 依赖 `SysOperationLogService`；因此不需要额外的 `PermissionQueryPort`、`OperationLogWriter` 或对应 Adapter。`system-api` 契约由各功能包的 Service 实现，不设一个汇总所有契约的 `SystemApiService`。
- Controller 负责请求 DTO 到响应 VO 的映射，Service 负责规则、授权范围及事务，Mapper 负责数据库读写；DTO、VO 不直接使用表实体。单实现业务类直接放 `service/`，如 `SysDictService`，Controller 和同模块其他 Service 注入该类；`@Transactional` 标在具体类的公共方法。辅助规则和组装类放所在功能的 `support/`。当存在多个实现或真实的跨模块边界时再定义接口，以职责命名且不加 `I` 前缀；跨 Maven 模块契约放 `admin-system-api`，不暴露业务模块内部 Service 或表实体。初始化器只调用系统 Service；内置超管的授权和唯一持有者保护由系统 Service 统一执行。[JeecgBoot 示例](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-module-system/jeecg-system-biz/src/main/java/org/jeecg/modules/system/service/ISysDictService.java)、[若依示例](https://github.com/yangzongzhuan/RuoYi-Vue/blob/master/ruoyi-system/src/main/java/com/ruoyi/system/service/ISysDictTypeService.java)使用接口/实现成对命名，这是其项目约定，并非 Java 或 Spring 对三层架构的要求。
- 接口权限由 Spring Security `@PreAuthorize` 判定；操作日志切面只采集标注的关键写操作，成功记录在业务提交后以新事务写入，失败记录使用独立事务。登录日志由认证 Service 单独写入；`auth/schedule` 只放 refresh 会话维护任务。
- Flyway 脚本统一放 `admin-system-start/src/main/resources/db/migration`，版本号全项目唯一。密钥用环境变量注入，不写入配置文件。

## T06 实际文件与后续接入

设计树中的代表性文件不全是已实现目录。T06 当前用户查询位于 `auth/controller/CurrentUserController`，HTTP 用户 VO 位于 `auth/vo`，路由 VO 位于 `menu/vo`；授权查询和组装为 `permission/{PermissionService,PermissionGraph,mapper/PermissionMapper}`。`AuthorizationChangeService` 提供业务事务内版本更新与提交后缓存失效；`common/annotation/OperationLog`、`log/aspect/OperationLogAspect`、`log/service/SysOperationLogService` 和 `log/mapper/SysOperationLogMapper` 提供审计写入。新增 Boot 4 的 `spring-boot-starter-aspectj`，版本由 Boot BOM 管理。

现阶段没有其他业务 Maven 模块消费当前用户或权限查询，`admin-system-api` 不提前建立无人调用的契约；有真实消费者时再加入只读接口和 DTO。T07 及后续管理 Controller 声明 `@PreAuthorize`，Service 写方法声明业务事务与 `@OperationLog`，并在同一事务中调用授权版本更新辅助方法。`@OperationLog` 不代替接口授权，也不采集完整业务载荷。

## T07 实际菜单模块

`menu/controller/SysMenuController`、`dto/SysMenuSaveDTO`、`vo/SysMenuVO`、`service/SysMenuService` 实现管理契约；`support/SysMenuRules` 处理完整路径和层级，`support/SysMenuInput` 做元数据与组件白名单转换，既有 `mapper/SysMenuMapper` 增加菜单写锁、内置授权、关联清理和显式可空更新。页面键清单位于业务模块 `src/main/resources/menu-components.txt`，T14/T15 新增入口时同步维护。动态路由仍由 T06 独立 VO 输出；两类树共用安全显示元数据组装。

## T08 实际部门模块

`dept/controller/SysDeptController`、`dto/SysDeptSaveDTO`、`vo/SysDeptVO`、`service/SysDeptService` 已实现；`support/SysDeptTree` 统一树校验、字符串 ID 和稳定排序，既有 `mapper/SysDeptMapper` 增加结构写锁、目标部门锁、关联用户计数和显式可空更新。未新增 Maven 模块、表或跨模块查询契约；没有实际消费者时不预建 `SysDeptQuery`。

## 4. 新增业务模块

以后开发电商管理系统时，按系统模块的方式增加 `admin-mall-api` 与 `admin-mall-biz` 两个 Maven 模块，仍由 `admin-system-start` 装配成同一个 Jar。`api` 对外提供确实需要跨模块调用的 Java 查询契约和只读 DTO；`biz` 实现电商功能、HTTP 接口及这些契约。电商内部的 Controller、Service、Mapper 无须经过 `api` 相互调用。

```text
admin-mall-api/
  pom.xml
  src/main/java/com/maplehush/admin/mall/api/
    product/ProductQuery.java              # 其他业务模块需要商品数据时定义
    product/ProductDTO.java
admin-mall-biz/
  pom.xml
  src/main/java/com/maplehush/admin/mall/
    product/{controller,dto,service,mapper,entity}
    order/{controller,dto,service,mapper,entity}
    inventory/{controller,dto,service,mapper,entity}
    aftersale/{controller,dto,service,mapper,entity}
```

`admin-mall-biz` 依赖 `admin-base-core`、`admin-mall-api`；需要当前用户、部门或权限判断时再依赖 `admin-system-api`，不直接依赖 `admin-system-biz` 或读取其表实体。`admin-mall-api` 不依赖 `admin-mall-biz`，也不放 Controller、Mapper、数据库实体；没有跨模块消费者的功能只留在 `biz`。`admin-system-start` 依赖 `admin-system-biz` 和 `admin-mall-biz`，负责统一启动。电商接口用小写 `mall:resource:action` 权限码，业务表使用 `mall_` 前缀，迁移脚本继续纳入统一 Flyway 版本序列。新模块内部仍遵循相同的 Controller → Service → Mapper 规范。
