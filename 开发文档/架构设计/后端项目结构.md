# 后端项目结构

本页只说明后端目录、依赖和新增业务模块规则。总体方案与 Vben 接口契约见[总体架构](./总体架构.md)。Maven `groupId` 为 `com.maplehush`，Java 包前缀为 `com.maplehush.admin`。

## 1. 模块职责

| 模块 | 职责 |
| --- | --- |
| `admin-base-core` | 公共响应、异常、实体时间基类、常量、工具、JWT 基础能力、Redis 公共配置、操作审计注解、MyBatis-Plus 配置和可复用的阿里云 OSS 存储能力 |
| `admin-system-api` | 当前用户、权限判断、部门查询等内部 Java 契约 |
| `admin-system-biz` | 认证（含图形验证码和强制改密）、用户（含 OSS 头像）、角色、菜单、部门、字典、日志及 HTTP 接口 |
| `admin-system-start` | 唯一启动类、环境配置、Flyway 和集成测试；唯一可执行 Jar |

这是**四个 Maven 子模块、一个 Spring Boot 进程**。`admin-system-biz` 和以后新增的业务模块按功能分包，包内统一为 Controller → Service → Mapper；`base-core` 和 `start` 承担公共技术与装配职责。[JeecgBoot 的 base-core、system-api、system-biz、system-start](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/pom.xml)是模块划分参考。

`common` 与 `config` 是 `admin-base-core` 内的 Java 包，不是额外 Maven 模块。`common/constant`、`util`、`annotation` 等均有首版用途；系统专属权限码留在 `admin-system-biz`。`common/entity/BaseEntity` 仅复用 `createTime`、`updateTime`；六个含这两列的系统主表实体继承它，主键仍由各实体声明。只有 `create_time` 的关联、会话和日志实体不继承它。系统管理资源统一以 `Sys` 开头，部门统一用 `Dept`：如 `sys_dept` ↔ `SysDept`、`SysDeptMapper`、`ISysDeptService`、`SysDeptServiceImpl`、`SysDeptController`。实体类放 `entity` 包，类名不加 `Entity` 后缀，参照 JeecgBoot 的 [`entity/SysUser.java`](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-module-system/jeecg-system-biz/src/main/java/org/jeecg/modules/system/entity/SysUser.java)。`Sys` 是 Java 类名约定，包名与接口路径仍为 `dept`；认证和当前用户能力保持 `Auth...`、`CurrentUser...` 命名。接口入参放 `dto` 包，以 `DTO` 结尾，如 `LoginDTO`、`SysUserSaveDTO`，不叠加 `Request` 后缀；面向前端的出参放 `vo` 包，以 `VO` 结尾，如 `CurrentUserVO`；跨模块 API 数据对象也以 `DTO` 结尾，不复用 HTTP 的 VO。`Result<T>`、`PageResult<T>` 是公共响应容器，不按业务 VO 命名。借鉴 JeecgBoot 的 [`AutoLogAspect`](https://github.com/jeecgboot/JeecgBoot/blob/main/jeecg-boot/jeecg-boot-base-core/src/main/java/org/jeecg/common/aspect/AutoLogAspect.java) 采集关键操作，但切面实现在 `admin-system-biz/log`，直接调用日志 Service；字典翻译和数据权限切面不进入当前范围。

验证码能力放 `system-biz/auth`：`AuthController` 提供 `GET /api/auth/captcha`，`IAuthRedisService` 的实现用 Redis 保存 2 分钟答案并原子消费，`LoginDTO` 带 `captchaId/captchaCode`。登录限流和当前用户最小快照也由 `system-biz/auth` 实现，公共 Redis 连接、序列化与键前缀配置放 `admin-base-core/config`；不新建验证码表或 Maven 模块。四个配置文件及职责见[Redis 与环境配置设计](./Redis与环境配置.md)。`admin-base-core/common/storage` 只封装 OSS Java SDK、配置、上传、删除、公开 URL 拼接和私有对象签名读取，不判断某个用户能否修改头像；`system-biz/user` 负责文件校验、当前用户绑定、将头像公开 HTTPS URL 写入 `sys_user.avatar_url`，以及从受控 URL 提取 Key 清理旧对象。以后 `admin-mall-biz` 可复用同一存储能力，在自己的业务接口落实商品图片等权限和限制，不依赖 `system-biz` 的上传 Controller。

密码规则和临时密码的哈希处理在 `system-biz/auth/support/PasswordPolicy` 统一实现：创建用户、管理员重置和首次超级管理员引导均使用约定的临时密码 `12345678`，正式改密仍校验新密码规则并禁止继续使用该值。`SysUser.mustChangePassword` 对应 `sys_user.must_change_password`。`IAuthService` 的实现在待改密状态只签发专用短期凭据，由 `AuthTokenService` 验证其类型、有效期和授权版本；`AuthSecurityConfiguration` 确保该凭据不能调用普通业务接口。`ISysUserService` 的实现在创建、重置和改密时负责更新用户标记、授权版本与会话，重置他人密码不会让操作管理员退出。创建/重置响应不返回密码明文，用户列表、详情和日志也不包含密码。`AdminBootstrapRunner` 仅在空库且 `ADMIN_BOOTSTRAP_ENABLED=true` 时创建首个超管。

## 3. 依赖与调用规则

```text
admin-base-core ────────┐
                        ├──> admin-system-biz ──> admin-system-start
admin-system-api ───────┘
```

- `admin-system-biz` 依赖 `admin-base-core` 和 `admin-system-api`；`admin-system-start` 装配业务模块。`admin-system-api` 只放跨模块需要的内部查询接口与只读 DTO，不放业务实体或写入接口；同一 Maven 构建内同步修改契约与实现。
- `base-core` 提供 JWT 校验、通用响应和 `@OperationLog` 注解，不查询系统表。`system-biz/auth/security/AccessTokenFilter` 查询用户状态与权限，`system-biz/log/aspect/OperationLogAspect` 依赖 `ISysOperationLogService`；因此不需要额外的 `PermissionQueryPort`、`OperationLogWriter` 或对应 Adapter。`system-api` 契约由各功能包的 Service 实现，不设一个汇总所有契约的 `SystemApiService`。
- Controller 负责请求 DTO 到响应 VO 的映射，Service 负责规则、授权范围及事务，Mapper 负责数据库读写；DTO、VO 不直接使用表实体。业务 Service 一律采用 JeecgBoot 风格的接口/实现命名：`service/ISysMenuService` 与 `service/impl/SysMenuServiceImpl`，调用方注入接口；事务与审计注解标在实现类公共方法。接口只暴露实际业务能力，不默认继承通用 CRUD，以免绕过授权、规则和审计。辅助规则和组装类放功能包的 `support/`；过滤器与令牌组件放 `security/`，装配放 `config/`，调度放 `schedule/`，引导放 `bootstrap/`，不强行为这些组件抽 Service 接口。跨 Maven 模块只读契约仍放 `admin-system-api`，有真实消费者时才建立，不把业务内部接口或表实体整体搬入 API 模块。初始化器调用业务 Service，内置超管授权和唯一持有者保护由业务统一执行。
- 接口权限由 Spring Security `@PreAuthorize` 判定；操作日志切面只采集标注的关键写操作，成功记录在业务提交后以新事务写入，失败记录使用独立事务。登录日志由认证 Service 单独写入；`auth/schedule` 只放 refresh 会话维护任务。
- Flyway 脚本统一放 `admin-system-start/src/main/resources/db/migration`，版本号全项目唯一。密钥用环境变量注入，不写入配置文件。

## T06 实际文件与后续接入

设计树中的代表性文件不全是已实现目录。T06 当前用户查询位于 `auth/controller/CurrentUserController`，HTTP 用户 VO 位于 `auth/vo`，路由 VO 位于 `menu/vo`；授权查询和组装为 `permission/{service/IPermissionService,support/PermissionGraph,mapper/PermissionMapper}`。`IAuthorizationChangeService` 提供业务事务内版本更新与提交后缓存失效；`common/annotation/OperationLog`、`log/aspect/OperationLogAspect`、`log/service/ISysOperationLogService` 和 `log/service/impl/SysOperationLogServiceImpl` 和 `log/mapper/SysOperationLogMapper` 提供审计写入。新增 Boot 4 的 `spring-boot-starter-aspectj`，版本由 Boot BOM 管理。

现阶段没有其他业务 Maven 模块消费当前用户或权限查询，`admin-system-api` 不提前建立无人调用的契约；有真实消费者时再加入只读接口和 DTO。T07 及后续管理 Controller 声明 `@PreAuthorize`，Service 写方法声明业务事务与 `@OperationLog`，并在同一事务中调用授权版本更新辅助方法。`@OperationLog` 不代替接口授权，也不采集完整业务载荷。

## T07 实际菜单模块

`menu/controller/SysMenuController`、`dto/SysMenuSaveDTO`、`vo/SysMenuVO`、`service/ISysMenuService` 和 `service/impl/SysMenuServiceImpl` 实现管理契约；`support/SysMenuRules` 处理完整路径和层级，`support/SysMenuInput` 做元数据与组件白名单转换，既有 `mapper/SysMenuMapper` 增加菜单写锁、内置授权、关联清理和显式可空更新。页面键清单位于业务模块 `src/main/resources/menu-components.txt`，T14/T15 新增入口时同步维护。动态路由仍由 T06 独立 VO 输出；两类树共用安全显示元数据组装。

## T08 实际部门模块

`dept/controller/SysDeptController`、`dto/SysDeptSaveDTO`、`vo/SysDeptVO`、`service/ISysDeptService` 和 `service/impl/SysDeptServiceImpl` 已实现；`support/SysDeptTree` 统一树校验、字符串 ID 和稳定排序，既有 `mapper/SysDeptMapper` 增加结构写锁、目标部门锁、关联用户计数和显式可空更新。未新增 Maven 模块、表或跨模块查询契约；没有实际消费者时不预建 `SysDeptQuery`。

## T09 实际角色模块

`role/controller/SysRoleController`、`dto/SysRoleSaveDTO`、`dto/SysRoleQueryDTO`、`vo/SysRoleVO`、`service/ISysRoleService` 和 `service/impl/SysRoleServiceImpl` 已实现角色 CRUD/分页与合并授权。`support/SysRoleGrantRules` 规范化 ID、目录祖先与页面/按钮关系；既有 `SysRoleMapper` 增加共享写锁与显式可空更新，`SysRoleMenuMapper` 批量读取/替换菜单关联并清理用户关联。权限变更复用 T06 的事务内版本辅助服务，日志复用 T06 注解与独立事务写入，不新增接口适配层、Maven 模块或无消费者的跨模块契约。

## 4. 新增业务模块

以后开发电商管理系统时，按系统模块的方式增加 `admin-mall-api` 与 `admin-mall-biz` 两个 Maven 模块，仍由 `admin-system-start` 装配成同一个 Jar。`api` 对外提供确实需要跨模块调用的 Java 查询契约和只读 DTO；`biz` 实现电商功能、HTTP 接口及这些契约。电商内部的 Controller、Service、Mapper 无须经过 `api` 相互调用。

```text
admin-mall-api/
  pom.xml
  src/main/java/com/maplehush/admin/mall/api/
    product/ProductQuery.java              # 其他业务模块需要商品数据时定义
    product/ProductDTO.java
admin-mall-biz/
  pom.xml
  src/main/java/com/maplehush/admin/mall/
    product/{controller,dto,service/impl,mapper,entity}
    order/{controller,dto,service/impl,mapper,entity}
    inventory/{controller,dto,service/impl,mapper,entity}
    aftersale/{controller,dto,service/impl,mapper,entity}
```

`admin-mall-biz` 依赖 `admin-base-core`、`admin-mall-api`；需要当前用户、部门或权限判断时再依赖 `admin-system-api`，不直接依赖 `admin-system-biz` 或读取其表实体。`admin-mall-api` 不依赖 `admin-mall-biz`，也不放 Controller、Mapper、数据库实体；没有跨模块消费者的功能只留在 `biz`。`admin-system-start` 依赖 `admin-system-biz` 和 `admin-mall-biz`，负责统一启动。电商接口用小写 `mall:resource:action` 权限码，业务表使用 `mall_` 前缀，迁移脚本继续纳入统一 Flyway 版本序列。新模块内部仍遵循相同的 Controller → Service → Mapper 规范。

## T09 后的分层结构调整

2026-10-14 按用户要求，将已实现的 11 个业务 Service 全部拆为 `I...Service` 与 `...ServiceImpl`；认证模块按职责归包，登录审计迁入 `log/service`。上方认证和权限树为调整后的实际文件；用户、字典、OSS 等尚未实施的条目仍为规划。详见[分层重构记录](./后端分层重构记录.md)。

## support 包的职责与边界

`support` 是现有功能包内的辅助分类，不是新增的 Maven 模块或第四层架构，也不是必须照建的目录。JeecgBoot 参考工程常把工具放 `util`、业务规则放 Service 实现；本项目只保留下列已有且有具体用途的辅助类，不要求后续每个功能都增加 `support`。

| 当前辅助类 | 具体用途 | 拆分理由 |
| --- | --- | --- |
| `auth/support/PasswordPolicy` | 新密码与临时密码规则 | 认证改密与首次引导共用，避免安全规则分散 |
| `auth/support/AuthDigests` | 登录限流标识与 refresh 凭据的 SHA-256 摘要 | Redis 和会话服务共用同一实现 |
| `menu/support/SysMenuInput` | 菜单表单转换、元数据/页面组件白名单 | 包含多类菜单输入规则与资源清单加载 |
| `menu/support/SysMenuRules` | ID、完整路径、父子层级、重复和循环校验 | 转换及写操作共同依赖完整路径规则 |
| `dept/support/SysDeptTree` | 部门树组装与父子层级校验 | 集中处理稳定排序、根节点及循环规则 |
| `role/support/SysRoleGrantRules` | ID 校验、授权节点及目录祖先关系规范化 | 角色授权服务复用规范化规则，查询 DTO 复用业务异常构造；范围校验仍在 Service |
| `permission/support/PermissionGraph` | 有效权限码和用户动态路由计算 | 处理目录祖先、按钮和页面的完整授权关系 |

简单、只使用一次的逻辑优先写在 `...ServiceImpl` 私有方法中；真正通用且不含业务规则的工具才放 `util`，不将业务逻辑统一搬到公共模块。后续新增辅助类必须有明确的复杂度或复用理由，不能只因名称带“规则”就拆类。

## T10 实际用户模块

`user/controller/SysUserController`、四个请求 DTO、`vo/SysUserVO`、`service/ISysUserService`、`service/impl/SysUserServiceImpl` 已接入七个管理接口。`SysUserMapper` 负责安全行锁投影、资料更新、密码哈希重置及目标会话撤销/清理，新增 `SysUserRoleMapper` 负责关联投影与全量替换；分页通过 MyBatis-Plus 安全投影及批量角色关联查询组装，避免 N+1。实体 password 标记 `@TableField(select=false)`，管理 DTO/VO 不接收或返回凭据。

用户写操作复用角色/菜单/部门的内置角色互斥行，再锁用户并复核操作者版本；角色范围、唯一超管保护、版本/会话变更均在同一业务事务中完成。资料修改不改变权限版本，提交后清理资料快照；审计沿用已有切面和独立事务。没有新增 `support` 类、Maven 模块、Flyway 版本或无消费者的 API 契约。头像、本人口令更新和 OSS 仍由 T13 实施。

## T11 实际字典模块

`dict/controller/SysDictController` 提供类型/项管理与有效选项查询共 11 个端点。`dto/{SysDictTypeSaveDTO,SysDictItemSaveDTO,SysDictQueryDTO}`、`vo/{SysDictTypeVO,SysDictItemVO,SysDictOptionVO}` 与实体分离；业务使用 `service/ISysDictService` 和 `service/impl/SysDictServiceImpl`，未新建 support 类。

现有 `SysDictTypeMapper` 增加类型行锁与显式更新，`SysDictItemMapper` 增加项行锁、清除旧默认和显式更新；锁查询将 `is_default` 显式别名为 `defaultItem`，避免通用下划线映射遗漏该业务属性。写入顺序为共享授权互斥行→操作者行→所属类型行→目标项行，清旧默认/写新默认在同一事务完成；唯一值冲突会回滚旧标记，类型删除与字典项创建也使用同一父行锁。

沿用 V1/V2/V3 表结构和已有字典菜单、权限及审计底座，不增加 Maven 模块、迁移、参数管理或字典缓存。详情和列表包括停用项；普通选项查询仅返回启用类型下的启用项，颜色保存小写并可显式清空。
